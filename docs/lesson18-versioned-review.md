# 第十八课：批准的是哪一个版本

这一批实现本地候选登记、版本检查、审阅决定、重复请求处理和审计复核。现有真实模型候选已经登记，**第 1 版，待审阅，没有批准，也没有部署。** 本批不调用模型，不增加 API 费用。

## 1. 为什么只加一个 approved=true 不够

假设你看过一条规则：“金额超过 329.90，同时近期没出现过该商户”，以及它新增 22 笔欺诈标签、2,863 笔正常审核的报告。

如果有人后来把金额门槛改低，命中范围就变了；即使规则名称相同，原先的结论和批准也不能继续算数。另一种情况是规则没改，但评测数据、基线或报告改了，审阅依据同样变了。

所以登记的不是一个规则名字，而是“一份具体材料包”：规则、候选提议、回放报告、来源关联和验证记录。程序为整包内容计算哈希指纹。内容变了，指纹就变；新材料需要新版本，重新进入待审阅。

哈希用于检查内容一致，不是加密，也不能证明是谁签字。

## 2. 版本怎样走

```text
登记材料 → 第 1 版 pending_review
                  ├─ 本地审阅批准 → approved
                  └─ 本地审阅拒绝 → rejected

材料改变 → 登记第 2 版 → pending_review（不继承第 1 版决定）
```

即使还没登记第二版，只要当前源材料与第一版指纹不一致，查询时也会显示 source_changed_requires_new_version，不能显示当前材料已批准。

同一版只能形成一个最终审阅决定。本版尚未提供撤销决定的专门流程；也没有任何生产发布工具。这里的 approved 只表示本地研究候选的审阅记录，不意味着准许执行真实策略。

Git 提交记录的是代码变化；这里的候选版本记录审阅材料变化。两者服务于不同对象。

## 3. 怎么防止看错版本和重复提交

每次写入都要说明 expected_version，意思是“我是在第几版的基础上提交的”。如果数据库已经变成另一版，就拒绝这次写入，防止拿旧页面覆盖新状态。这种做法叫乐观并发检查。

每次写入还有 request_id，可以理解为提交单号。同一单号、同一内容重复送达，只记录一次；同一单号换成不同内容，拒绝处理。这叫幂等。

一个容易忽视的细节：旧的批准请求重发，返回的历史回执可能仍写着“第一版批准”。它不等于当前版本也批准。因此 CLI 最后总会重新查询当前版本和当前材料，而不是拿旧回执当权限。

## 4. 审计记录保存什么

SQLite 中保存当前状态、每次命令和结果，以及提交单号。事件还记录前一条事件的哈希，形成链。

复核时不仅检查哈希链，还会从历史事件重新演算当前状态，再与数据库当前状态、重复请求回执比较。意外改动事件、状态表或回执，都可能导致检查失败。状态、事件和回执在同一事务中提交，失败不会留下半套记录。

这不是不可篡改存储：拥有本地数据库写权限的人仍可能重写整套历史。本地操作人名称也不是企业身份认证。项目当前证明的是版本、事务、幂等与一致性检查，不能称为完成生产权限治理。

## 6. 你可以运行什么

在项目根目录查看现有候选，不联网、不计费：

```powershell
.\.venv\Scripts\python.exe -X utf8 -B -m app.cli.review_candidate status
.\.venv\Scripts\python.exe -X utf8 -B -m app.cli.review_candidate verify
```

第一条检查当前材料是否与登记版本一致；第二条复核记录。预期看到 pending_review，以及审计 passed、events=1。

首次登记命令本批已经执行；下面同一请求重复执行仍只保留原登记，不需要为了推进项目重复运行：

```powershell
.\.venv\Scripts\python.exe -X utf8 -B -m app.cli.review_candidate register --expected-version 0 --request-id case-467716-initial-v1
```

decide 命令要求明确的版本、材料指纹、approve/reject、理由和提交单号。当前阶段无需你立即做决定，尤其不能因为系统能运行就批准一条新增正常审核很多的规则。
