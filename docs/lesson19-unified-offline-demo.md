# 第十九课：一条命令把已有模块串起来

本批新增统一离线演示入口。它会真正生成新调查、新候选、新回放和独立演示审阅记录，而不是只打开上一批已经成功的报告。

先记住：**调查和候选的决策使用离线策略/Fake；查询、回放和验证会读取实际本地合成数据。模型调用数为 0，不需要密钥。** 真实模型成果仍保留在先前记录中，不能把本演示当作一次新的模型成功。

## 1. 这次解决了什么问题

此前候选生成和验证脚本固定指向某一次历史调查。虽然各模块能单独运行，但不能自然接上新调查。

现在候选命令增加 --investigation-summary 参数，复核程序也沿着保存的来源路径检查。统一入口把上一步输出的路径传给下一步，运行索引保存所有阶段和关键摘要的哈希。

这叫工作流编排：程序决定先后顺序和失败处理；其中某些阶段可以由模型做判断，其他阶段仍由普通代码完成。不是把每一步都命名为一个新 Agent。

## 2. 一次演示执行六个步骤

| 顺序 | 实际执行什么 | 成功标志 |
|---|---|---|
| 1 | 从冻结树模型名单选预警，构建 case 并离线调查 | 结论校验通过 |
| 2 | 对照原事实库核对调查 | 投影、工具回执及引用复核通过 |
| 3 | Fake 提出候选，程序冻结并在开发期回放 | 候选合规且回放完成 |
| 4 | 核对候选来源、规则及回放关联 | 来源关联检查通过 |
| 5 | 用独立 SQL 复算回放 | 新增、重叠等计数一致 |
| 6 | 在演示专用 SQLite 中登记候选 | 第 1 版待审阅，审计通过 |

第六步使用演示目录里的 demo-reviews.sqlite。真实候选仍保存在 runs/reviews.sqlite，没有被演示改动。两边都没有批准或部署操作。

## 3. 为什么要保存每一步的状态

假设前三步成功，第四步发现引用不一致。系统应该保存前三步的成果和第四步的失败，而不是显示“全流程成功”，也不应该让你完全不知道停在哪里。

workflow.json 在每步开始和结束时更新。可能的整体状态是 running、completed、failed 或 cancelled；只有所有步骤完成才写 completed。更新通过临时文件替换，避免把半段 JSON 当成完整记录。

子进程单步最长等待 180 秒。超时或中断时结束当前子进程，保存失败或取消状态，不自动重试。不涉及远程模型取消或费用撤回。

这批只做进度保存，**尚未实现从某个阶段自动恢复**。强制结束宿主进程也可能留下一份 running 记录；它不能被当成成功。后续恢复机制需单独设计，不能从“有 JSON 状态文件”推断已经具备持久任务平台能力。

## 5. 你现在只需要这一条命令

在项目根目录运行：

```powershell
.\.venv\Scripts\python.exe -X utf8 -B -m app.cli.project_demo
```

运行后打开输出目录里的 README.md。再看 workflow.json：先看顶层 status，再看 stages 中各步骤的 status，最后按 artifacts 查对应产物。

只核对已有演示索引，不重跑数据：

```powershell
.\.venv\Scripts\python.exe -X utf8 -B -m app.cli.project_demo --inspect runs/demo-offline-v1-b71c5fa75aff/workflow.json
```

这个检查核对整体状态、关键摘要哈希和上下游路径。详细交易事实、SQL 和审阅记录仍使用各自验证器；不能把索引检查当作重新独立算过全部数字。

## 6. 演示的前提与项目边界

演示依赖本机已构建的合成数据快照、特征、冻结模型名单和训练规则阈值。它不会自动下载数据或重新训练模型。因此现在是“当前项目环境下的一命令演示”，不是新电脑安装后即用的交付包。原课程仓库未修改。

项目已有的真实模型调查、真实提议与本地审阅可按之前文档独立核查。本入口暂不提供一键真实模型模式，避免把离线演示、额外计费与实际审批混在一起。

下一步的重点仍是更丰富的任务与同权限模型对照、保留评测、恢复/取消和交付说明。统一入口改善可复现性与展示，不替代对 Agent 实际价值的验证。
