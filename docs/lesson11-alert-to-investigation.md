# 第十一课：模型说值得检查，Agent 接下来查什么

这一课把检测实验接到调查流程。先记住：**分数高，意味着值得核查；它没有自动给出欺诈原因，更没有证明交易欺诈。**

本轮工具会读取真实存在的本地合成数据快照；决策部分先用明确写在 Python 里的离线演示策略。它不是大语言模型，也没有花 API 费用。我们先验证工具、证据和失败路径，再接真实模型。

## 1. 从一个具体例子理解调查

假设一笔交易被模型排到当天前 10 名。分析师想核查三个线索：此前一小时交易是否频繁、这笔金额是否高于近期通常出现的金额、商户是否在近期出现过。

这里第二项暂用一个很窄的检查：本笔正金额是否超过过去 30 天的正金额最大值。它不是完整的“偏离正常消费”模型，后续可以再讨论分位数等更合理的比较。

Agent 不应该直接说“高分，所以大额异常、陌生商户、疑似团伙”。它需要先请求工具：

```json
{"name":"summarize_history","arguments":{"lookback_hours":1}}
```

程序查询绑定用户、绑定截止时间以前的一小时。假设真实回执是 `prior_count=2`，那么“此前一小时至少 4 笔”的怀疑就不成立。模型即使先前倾向于怀疑频次，也必须接受这个结果。

交易次数由程序数，不让语言模型心算；模型负责选择下一步查什么，并引用证据。

## 2. 数据怎样流动

`冻结的模型审核名单 → 选一笔预警 → 生成单 case 事实库 → 请求工具 → 工具回执 → 补查或结束 → 代码核验 → 报告`

这次复用已经算好的树模型名单，不临时调整检测分数、不根据标签挑好看的案例。默认取冻结名单中第一条树模型记录，因此只是一次开发冒烟，不代表任务准确率。

每个 case 的事实库仅保存：目标交易本身，以及同一个用户在它之前最多 30 天的历史。其他用户、同刻其他交易和未来交易不写进去，标签表也不写进去。目标交易是允许读取的当前观察对象；历史统计只算严格早于它的记录。

这是字段和工具接口上的隔离，不是已完成服务器多租户权限系统。程序运行进程仍由项目拥有者控制，不能把本地文件分开就宣称生产安全验收。

## 3. 模型实际有哪些工具

| 工具 | 输入 | 返回什么 |
|---|---|---|
| get_alert_transaction | 空对象 | 当前交易、检测版本与分数、证据编号 |
| summarize_history | 1、24、168、720 小时之一 | 此前次数、带符号金额净和、正金额最大值、覆盖情况与少量预览 |
| query_target_merchant | 同样的允许窗口 | 目标商户 ID 在用户此前历史中出现几次，以及证据编号 |

不接受 user_id、as_of、文件路径或 SQL，因为这些范围已经绑定。模型不能通过把时间改成明年、用户改成别人来补充资料，也没有读取文件、执行命令或查询标签的工具。

历史回执最多预览 3 条，但汇总会计算完整允许窗口。不能只数预览，就说窗口里一共 3 条；也不能把负金额直接称为退款，币种仍未知。

## 4. 两条补查路径是怎样来的

离线演示策略先读当前交易，再查一小时：

- 如果此前已经至少 4 笔，再查 24 小时作背景核对，报告频次线索。
- 如果一小时不频繁且覆盖完整，再查 30 天金额和目标商户，看看别的怀疑是否有证据。
- 如果覆盖不足且当前观察不足以支持频次判断，直接报告资料缺口。

这只是我们写的演示决策规则。它能测试“不同回执走不同后续工具”，不能证明真实模型学会了自适应调查。真实模型接入后仍使用同样工具与校验，再单独评测它选工具和处理缺口的能力。

## 5. Agent 控制循环在做什么

课程中的循环可以继续使用：

1. 把任务、工具说明和已有消息交给客户端。
2. 客户端返回工具请求，Agent 调用程序执行。
3. 程序返回 Observation，作为 `role=tool` 的消息放回历史。
4. 下一次客户端看到回执，选择继续查或提交结论。

本批的离线策略把这个“客户端”位置先占住。HTTP Mock 则假装兼容 Chat Completions 的接口返回消息，用来检查 HTTP/JSON 链路；两者都没有真实模型能力。

工具回执里的 `evidence_id` 是内容和快照关联的引用编号，不是大模型自己起的来源名字，也不是不可篡改的数字签名。轨迹记录的是工具请求、结果与结论引用，不声称获得完整的模型内部思考过程。

## 6. 为什么不直接保存模型写的一大段报告

本版先把最终输出收窄成结构化结论：

```json
{
  "findings": [{
    "check": "high_prior_frequency_1h",
    "assessment": "not_supported",
    "evidence_ids": ["工具实际返回的编号"]
  }]
}
```

代码检查：编号是否存在、是不是同一个 case、窗口是不是一小时、次数是否真达到 4、覆盖不足时有没有乱下结论。通过后，再由程序把已核对数字填入中文报告。

因此第一版不允许模型随便新增数字或自由写“已确认欺诈”。它只核对三项预先定义的线索。这个约束降低了输出自由度，但让我们能精确测试。以后扩大调查类型时，需要同步增加证据口径和评测任务。

三个状态分别表示：

- supported：证据支持这一项线索，不等于确认欺诈。
- not_supported：证据不支持这一项线索，不等于确认交易安全。
- insufficient_evidence：资料不足，不把没查到当作不存在。

“过去没见过商户 ID”只能限定到该用户和该时间窗，也不能解释成商户刚成立。没有正金额历史，无法比较金额最大值，应报告资料不足。

## 7. 失败时会怎样

越界参数和未知工具返回错误，也会消耗调用预算。默认最多 6 次工具尝试、8 次客户端轮次，每轮最多 3 个工具请求；还限制上下文和最终输出字符数。字符预算不是 token 计费预算，真实接口费用控制下一批另做。

伪造引用、错误结论或额外自由文本会使报告拒绝发布。达到迭代上限、HTTP/协议失败也不会标成调查成功。输入投影或文件指纹改变时，先停止而不是继续用错版本。

这些是可测试的原型边界，后续还需要真实模型 usage、超时、取消、持久恢复、独立任务集与权限部署。

## 8. 自己运行

```powershell
.\.venv\Scripts\python.exe -B -m pytest -q -p no:cacheprovider tests/test_case_investigation.py
.\.venv\Scripts\python.exe -X utf8 -B -m app.cli.investigate_case
```

第二条命令使用现有冻结模型名单和研究快照，创建新的 case 目录，打印结果并保存中文报告、消息历史和工具证据。它不读取 API Key、不联网、不打开标签库。

先读 `app/risk/investigation.py` 的 `run_investigation`，看它怎样复用课程 Agent，再看 `app/tools/case_tools.py` 的 `dispatch`。`app/llm/offline_investigator.py` 是明确写死的演示策略，不要把它当成训练出来的模型。
