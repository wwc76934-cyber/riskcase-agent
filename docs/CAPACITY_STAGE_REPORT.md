# G3-A 阶段验收：相同审核容量下的规则验证

验收日期：2026-10-21。阶段已完成，**不代表候选规则被批准或整个项目已结项**。

## 回答了什么产品问题

Agent 之前根据开发案例的证据，选择“较大正金额、完整历史、有历史但商户未见”的模板，形成一个受限候选。它与此前手工规则条件相同，不是新的算法发现。

追加审核回放曾显示：在树模型每天 10 笔之外，再审核额外 2,885 笔，可新增捕获 22 个欺诈标签，同时新增 2,863 个非欺诈标签审核。但如果每天只能审核 10 笔，候选会挤出谁？新增捕获能否抵消挤出损失？本阶段实际回答了这个问题。

## 已完成的完整链路

已有证据约束的 Agent 候选 → 冻结规则、输入和容量政策 → 不读取标签地分配名单 → 保存名单指纹 → 宿主端读取开发标签 → 配对统计新增与挤出 → 独立 SQL 重算 → 材料绑定到候选新版本 → 导出人可读比较报告。

原始规则与提议来源保留。新增材料登记到 `case-467716-rule` 第 2 版，状态 `pending_review`；当前材料哈希一致，未批准、未部署。旧版本决定不能自动继承到新材料，本次没有代替人工作出采纳/拒绝决定。

## 冻结的比较口径

数据为 IBM TabFormer 合成快照的 2018 年开发部分：422,088 笔、683 个欺诈标签、365 个有记录日期。捕获和非欺诈审核均按源标签计算，不表示现实案件确认。

预算预先固定为每日最多 5、10、20 笔，**10 笔为主口径**。四种政策：

| 政策 | 具体分配方法 |
|---|---|
| 树模型 | 按已冻结 HGB 分数每日取前 K 笔 |
| 规则单独筛选 | 只取命中候选的记录，按金额排序；不足时空置 |
| 规则保留20%名额 | 先取 floor(K/5) 个命中候选中 HGB 分数最高者，其余按 HGB 补齐并去重 |
| 规则优先 | 先在命中候选中按 HGB 排序，再用非命中记录补齐 |

分数相同沿用原模型实验的固定哈希顺序。主预算的树模型名单与原有 3,650 笔名单逐 ID 完全一致。政策、阈值、预算和 9 份执行代码指纹在本轮标签读取前冻结，没有看完结果再调保留比例。

“相同容量上限”不等于每种政策实际审核量相同：规则单独筛选会空置名额。两种组合方案与模型在本数据上实际审核量相同，可以直接比较捕获和正常审核。

这仍是日终批量审核，不是交易发生时的实时拦截。不能把全日排名用于声称实时可用性。

## 主口径结果：每日最多10笔

| 方案 | 实际审核 | 捕获标签 | 非欺诈审核 | 新增捕获 | 挤出损失 | 净变化 |
|---|---:|---:|---:|---:|---:|---:|
| 树模型 | 3,650 | 95 | 3,555 | 0 | 0 | 0 |
| 规则单独筛选 | 2,791 | 33 | 2,758 | 17 | 79 | −62 |
| 规则保留20%名额 | 3,650 | 90 | 3,560 | 11 | 16 | −5 |
| 规则优先 | 3,650 | 62 | 3,588 | 21 | 54 | −33 |

“保留20%”替换了 543 个审核名额：新增捕获 11 笔，但失去原名单的 16 笔，净减少 5 笔。规则优先虽然新增捕获 21 笔，却挤出了 54 笔。因此之前的追加审核结果不能作为同预算采纳依据。

**本阶段建议：主预算保留树模型方案，不依据这些开发结果为候选预留或优先分配名额。** 这是一项研究建议，正式本地审阅仍待人工处理。

## 次要预算与稳定性

“保留20%”在每日 5 笔时捕获 56 个标签，相对同预算树模型的 50 个，净增加 6 个；每日 20 笔时捕获 159 个，相对 163 个净减少 4 个。两档都完整保留，不能挑出每日 5 笔后改称主实验成功。

主预算下，“保留20%”在 4 个月净增加、5 个月净减少、3 个月持平。月份分解只是描述，不能当作独立验证，也没有据此拟合按月切换政策。

完整 12 组结果与月度表见 [可展示比较报告](../examples/capacity-comparison.md)，冻结指纹与原始统计见 [阶段结果 JSON](capacity-stage-v1-results.json)。

## 必须保留的解释边界

- 2018 年数据已被此前检测比较与候选回放使用，本阶段不是新的未见保留集。先冻结本轮政策，只能防止本轮边看结果边调，不能消除历史开发偏差。
- 数据为合成数据；不知道真实损失、审核成本和标签确认时间，不能计算真实利润或声称在线收益。
- 独立 SQL 是独立计算复核，不等于独立数据或业务有效性验证。2019 年检测最终测试继续封存。
- 该候选主口径表现较差，只能说明当前规则及分配方法没有得到采纳支持，不代表所有规则或所有 Agent 无效。
- 没有为了优化数字而自动修改规则、搜索阈值、批准候选或连接账户/支付系统。

## 查看与复核

直接阅读 [比较报告](../examples/capacity-comparison.md) 即可查看所有预算，不必先读代码。

在项目根目录独立复核已有运行，不调用模型、不重新选规则、不改变审阅决定：

```powershell
.\scripts\run_project.ps1 -m scripts.verify_capacity_experiment --directory runs/capacity-stage-v1
```

导出可读报告：

```powershell
.\scripts\run_project.ps1 -m scripts.export_capacity_report --directory runs/capacity-stage-v1 --destination examples/capacity-comparison.md
```

如需从头复现，用一个不存在的新目录；不能覆盖已冻结材料：

```powershell
.\scripts\run_project.ps1 -m app.cli.capacity_experiment freeze --directory runs/capacity-reproduction
.\scripts\run_project.ps1 -m app.cli.capacity_experiment plan --directory runs/capacity-reproduction
.\scripts\run_project.ps1 -m app.cli.capacity_experiment evaluate --directory runs/capacity-reproduction
.\scripts\run_project.ps1 -m app.cli.capacity_experiment verify --directory runs/capacity-reproduction
```

`register` 是独立的研究材料登记步骤，不是批准；`all` 会顺序执行冻结、规划、评估、核验和登记。规划与评估拒绝覆盖已有结果。需要现有数据、特征和模型快照；原始 SQLite/NPZ 在忽略目录中，当前还不是干净机器无前提的一键复现。
