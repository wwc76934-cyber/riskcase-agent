# 第四批：先说明数据，再讨论模型

本批目标是验收固定来源的数据分布与基本质量，为后续建模样本合同提供依据。不是训练检测器，也不是让大模型读取全部交易。

## 先看一条交易代表什么

以下为自建教学示例，不是上游记录：用户 A 的卡 0，在某日 10:00，向商户 M 交易 120 个源金额单位；标签为 Yes。

事实包括谁、何时、商户、金额；标签是评测答案。金额高并不说明欺诈，标签为 Yes 也不能说明原因一定是大额。解释必须由可核查证据支持，缺少原因就保留未知。

## 本批程序如何工作

`app/cli/profile_data.py` 先检查本地归档大小和完整 SHA-256，然后顺序读取 CSV，将一行一行的字典交给 `app/risk/profiling.py`。不联网、不把归档解压到文件夹、不调用模型、不把 2,400 多万行同时载入内存。

统计器检查必需字段、日历时间、有限金额与 Yes/No 标签。非法行单独计数，不能默认为正常交易。某行可以有多个错误，因此错误原因次数可能大于被拒行数。

它维护按年、月、用户和渠道分组的行数、正例数、时间范围，以及不同用户/卡/商户的集合。这就是分组聚合：相同键的记录累积到同一个分组。数据较小时，我们后续会用 Pandas 的 groupby 表达同一种思路；本批采用标准库流式统计，便于复用现有环境并控制大文件内存。

读取到 CSV 结尾之后核对每种分组的行数与正例数能否加回总数，再发布 profile.json。半途失败不发布 complete 报告，目录存在不能代表运行成功。报告绑定源归档哈希、脚本哈希和 Git 提交。

报告位于本地忽略目录 data/profiles/profile-*/profile.json，包含评测用途的标签汇总，不注册为调查 Agent 工具。

## 看结果时的四个判断

1. 有多少正例、分布在哪里：决定样本能否训练和评测。不能为了凑正例专挑欺诈用户，再把结果称为普通用户总体表现。
2. 是否按时间排序：文件中相邻记录时间倒退不一定是坏数据，可能由不同用户或卡分组造成。构造历史窗口必须显式按实体和时间处理。
3. 哪些列缺失：Errors? 空白和必需金额缺失的业务含义不同；不能统一填 0。金额负数也需保留语义待核实。
4. 类型通过不等于业务正确：本批未完成业务重复、商户标识稳定性、位置合理性、标签确认时间与所有字段的泄漏审计。

## 自己运行

在项目根目录 PowerShell 运行完整剖析（复用本地归档，耗时数分钟）：

```powershell
.\.venv\Scripts\python.exe -B -m app.cli.profile_data
```

程序打印报告绝对路径和 SHA-256。每次创建新目录，不覆盖之前结果；无需为了看相同结果反复全扫。新统计测试：

```powershell
.\.venv\Scripts\python.exe -B -m pytest -q -p no:cacheprovider tests/test_risk_profiling.py
```

测试使用自建小样本检查非法标签不能变成负例、金额符号、卡号作用域、日期合法性、分组统计与时间倒退；不需要模型或网络。

## Agent 知识：数据探索不是每次调查都做

全源剖析属于离线数据准备，由可复跑代码执行。调查 Agent 只拿到预警和受限工具，在有限预算下访问该 case 必要的历史。把全源和标签直接塞进提示词，既浪费预算，也破坏评测与证据边界。

后续会将探索数据、训练特征、评测标签和调查可见视图分开管理。当前文件分离仍不等于完整权限沙箱，不能宣称已实现生产隔离。
