# 第三批：完整历史窗口与确定性查询工具

目标：从稀疏发现样本推进到可复核的历史统计工具，给后续调查 Agent 提供真实查询结果。本批不进行模型训练或付费模型调用。按用户新偏好，直接讲解与推进，不布置问答。

## 风控知识：统计口径先于规则

历史特征必须定义对象、时间窗口、边界和金额口径。例如“用户在过去 24 小时的交易次数”使用 `[t-24h, t)`：包含起点，排除当前交易时点及未来。若同一分钟有多笔事件而源没有更细时间/顺序，这个定义会排除所有与 t 相同的记录，不能自行推断分钟内先后。

这个边界区别于上一批的“当时可查询事实 `event_time <= cutoff`”：事实查询可以包含焦点交易，而计算纯历史特征时需要明确排除它。两种功能不能共用未经区分的边界。

频次异常不等于欺诈；阈值没命中也不等于正常。金额总和保留为源单位，币种仍未知，不能直接称人民币或预期损失。负金额保留，统计为带符号净和；后续业务可另定义正向交易额或退款口径。

完整性是相对于某个范围成立的：本工具只承诺登记用户、登记日期在固定合成源中的完整记录；不保证现实支付链路完整，也不保证当时已经入库、标签已经确认。

## 本批数据流

```text
官方固定归档
  → 分段缓存、响应范围校验、整包 SHA-256
  → 顺序扫描完整 CSV（不落地解压大表）
  → 仅保留登记用户与登记日期内的记录
  → facts/facts.sqlite（无标签）＋独立 evaluation-labels.jsonl
  → manifest（范围、来源、计数与事实库哈希）
  → UserHistoryTool 只读固定 SQL
  → Decimal 聚合＋有界证据列表＋覆盖状态
```

完整扫描没有全部存储进 SQLite。当前配置保留用户 0–7、2019-12-01（含）至 2020-01-01（不含）的交易。扫描完才发布 `ready` manifest；中断或坏输入不会生成可用的完整性声明。

初次普通下载超过五分钟预算，未发布成功归档；改为 4 MiB 分段、最多 8 路并发、严格核对 Content-Range、有限重试并保留已完成分段。只有整包大小和 SHA-256 均匹配后才发布缓存。下载与接入故障不转换为金融结论。

## Agent 开发知识：工具合同与边界

`UserHistoryTool` 是确定性工具，当前还没有接入 LLM。模型未来只提交 `user_id/as_of/lookback_hours/evidence_limit`，不能提交文件路径、任意 SQL 或标签请求。输入类型、窗口和结果预算由代码验证；SQL 用参数绑定，数据库以只读模式打开。

输出包含：

- `observed_count`、`observed_amount_sum`：实际查询到的统计。
- `window_complete_within_source_dataset`、`incomplete_reasons`：是否有覆盖证据。
- `evidence`：来源行号、交易引用和金额等事实。
- `evidence_truncated`：只限制展示条数，不影响完整聚合。
- `facts_sha256`：本次使用的事实库指纹；这是完整性核验，不是防篡改存储证明。

后续 Agent 把这个结构化结果作为 Observation，而不是只收到“查到两笔”的无上下文字符串。工具成功、数据完整与风险结论是不同状态。

本批已把它接入课程 Agent 的工具合同：`Toolset` Protocol 只约定 `schemas` 和 `dispatch`，原 BasicTools 和新 HistoryTools 都能满足它，无需让控制循环了解 SQLite。Schema 告诉模型工具叫什么、可提交什么参数；`dispatch` 的代码校验才真正执行权限和类型约束。只提供 Schema 而不验证参数不能形成安全边界。

离线端到端测试使用 Fake 发起 `query_user_history`，实际调用 SQLite，再核验第二次模型请求中的 tool 消息。Fake 证明工程闭环，不能证明真实模型会选对调查动作。新工具集不暴露 `read_file`、命令或任意 SQL。

示例阈值判断：

| 实际结果 | 返回含义 |
|---|---|
| 已观察到至少 5 条记录 | `met_in_observed_records`，仅说明条件在观测记录中满足 |
| 少于 5 条且窗口完整 | `not_met_in_complete_dataset_window`，只说明该条件未命中 |
| 少于 5 条且覆盖不足 | `unknown_incomplete_window`，不能推出规则未命中 |

5 只是教学配置，不是已验证业务阈值。

## 去重、谱系与快照

同一 `transaction_id`/物理行重复传入且内容一致时去重；同一引用内容冲突时失败。不同源行即使金额/时间相同，也不擅自合并，可能是真实的两笔交易。因此这里只证明“重复引用未重复计数”，业务交易唯一性还未建立。

快照库持久化、建立用户和时间索引，并绑定 SHA-256。加载时检查文件与 manifest 一致。manifest 本身不是签名可信锚，不能宣称可抵御有写权限者重写整套工件。

此阶段不需要向量库、微服务或多个 Agent，先把 SQL 查询、数值与证据接口做正确，再让模型决定查询顺序。

## 运行

第一次准备完整源会下载约 266 MiB 官方合成数据到忽略目录，仅作本地研究；以后校验并复用缓存。数据的公开再分发范围尚未确认，不提交归档和快照。

```powershell
.\.venv\Scripts\python.exe -B -m app.cli.build_history
.\.venv\Scripts\python.exe -B -m app.cli.history_demo --latest --user 0 --as-of 2019-12-15T12:00:00 --hours 24
.\.venv\Scripts\python.exe -B -m pytest -q -p no:cacheprovider tests/test_risk_history.py tests/test_archive_cache.py
```

第二条是历史查询，不触发模型。若查询越过登记日期，结果会标记不完整，而非补造缺失数据。

下一批：使用这些确定性查询结果生成版本化基线告警与 case，随后接入受限 Agent 工具循环。G0 的标签可得时间、再分发范围和真实匿名源仍需继续核验。

## 本批实测结果

- 固定归档大小与完整 SHA-256 匹配，完整 CSV 扫描 24,386,900 条。
- 用户 0–7 的登记一个月范围保留 765 条，标签全部为正常，仅可验证查询与正常反例。
- 用户 0 截至 2019-12-15 12:00，过去 24 小时：2 条、源金额净和 108.96；过去 168 小时：29 条、净和 2402.26。
- 截止时间为 2019-12-01、过去 24 小时越过范围，返回不完整与 unknown。
- 新增 20 个测试，全仓 86 个通过；Fake 发出调用、SQLite 真实查询、tool 消息回灌的端到端测试通过。并非真实模型调查效果验证。
- 完成快照在本工作区已经存在，直接运行 `history_demo --latest` 即可，不需重复下载或扫描。`build_history` 用于重建复现。
