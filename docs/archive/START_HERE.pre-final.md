## 我们要做什么

RiskCase Agent 是给支付风险分析师使用的反欺诈调查与规则验证工作台。分析师从一条预警出发，查询交易及历史行为，核对怀疑、整理证据，再验证一条候选规则会增加多少有效预警和误报。

最终输入：快照、告警、调查截止时间、问题与查询预算。
系统执行：确定性统计和检测 → Agent 根据结果选择补查工具 → 代码核验证据 → 人工审阅规则候选 → 独立保留集重放。
最终输出：可引用的调查记录、资料缺口、工具轨迹、规则候选与离线验证包。

目前这是开发目标，尚未全部实现。自动冻结、支付、认定犯罪不在范围内。

## 算法与 Agent 分别做什么

检测器把历史特征转换为规则命中或模型风险分数，负责筛出值得调查的预警。Agent 接收预警，通过工具寻找证据、选择进一步查询，并组织有依据的解释。工作流代码控制预算、权限、校验与状态。

举例（教学假设，非实验结果）：一笔大额交易命中规则。工具发现该用户平时金额也很高，且商户并不新。Agent 应降低对“大额即异常”的支持，说明仍缺哪些证据；不能只照着初始告警编故事。若短时间交易显著增多，则调用窗口工具核查次数和记录，而不能靠语言模型心算。

即使历史标签写着欺诈，也不代表工具查到的金额和频次足以解释原因。标签是检测评测的参考答案，调查证据是结论的依据，两者分别评估。

## 数据分析必须成为主线

| 问题 | 要做的分析 | 要留下的成果 |
|---|---|---|
| 数据能否用 | 行数、用户/商户数、日期、缺失、重复、金额符号、单位 | 可复跑质量报告和字段说明 |
| 能否建模 | 各时间段正负例、每用户覆盖、标签确认时点、源排序与采样偏差 | 建模样本合同和限制清单 |
| 什么值得检测 | 金额分位数、用户内偏离、短窗口次数、新商户、商户集中 | 图表、解释与按历史计算的特征 |
| 模型是否有效 | 规则、逻辑回归、一个树模型；按时间留出 | 固定告警预算的 Precision/Recall、AP 等明确口径 |
| 错在哪里 | 正常高消费、退款、新用户、不同时间段等误报/漏报分组 | 失败案例和改进依据 |

每项遵循：业务问题 → 统计口径 → 代码和图表 → 解释 → 限制。SQL 用于筛选、关联和聚合，Pandas/NumPy 用于整理与统计，Scikit-learn 用于基线和评测。PyTorch 首轮已训练并比较，后续模型改进继续沿用当前评测接口；下一步接入受控真实模型调查，见 [模型学习路线](model-learning-roadmap.md)。

训练与调查严格分权：训练代码需要训练标签，独立评测器需要保留标签；调查 Agent 不应读取目标欺诈标签。标签确认时间未知时，只能报告事件时间切分的回顾性实验，不能伪装成已验证的线上时点回放。

## 接下来按什么顺序做

1. 数据剖析与建模样本验收：复用已下载源，产出可复跑报告；先确定是否存在足够且分布合理的正例、完整历史和可解释字段。不因急于训练绕过数据问题。
2. 特征与检测对照：完整历史构建窗口特征，时间切分，训练规则/逻辑回归/一个树模型；先理解误报、漏报和告警预算。
3. Agent 调查：受限工具、至少两条依证据变化的补查路径、缺口终态、证据校验；再用小规模真实模型调用验证。
4. 规则验证：受限 JSON 规则、开发与保留隔离、增量捕获和新增误报、人工审阅。
5. 交付：恢复/取消/超时、CI、可复现演示、架构图和独立评测。界面服务于审阅，后置实现。

不再用问答测验作为推进条件。每批直接讲解输入、输出、计算口径、失败情况，附运行方式、结果说明和小步提交。当前已进入数据分析阶段，按本页最新进度推进。

## 怎样才有简历价值

至少具备可复现数据分析、诚实的检测对照、真实模型工具调查、独立任务评测与失败分析。Agent 要与相同数据权限的固定调查流程比较，证明自适应补查是否值得额外成本；没有提升也如实报告。

当前可描述的是已实现的数据与工具底座，不能写已提升欺诈识别率、调查效率或达到生产级。只有合成数据时可以交付工程原型，但不能声称已证明真实支付业务效果；真实匿名数据若缺实体键，也只能验证其支持的分类任务，不能拼接成虚假的完整客户调查。

GNN、VAE、多 Agent 都不是验收门票。是否加入，由数据结构、明确失败问题、基线对照和资源决定。项目工程质量可以用测试与评测证明，“企业级”还需要真实集成、权限治理、运行与业务验收，不能仅凭架构名称认定。
