对本项目最直接的设计参考是 Dexter。TradingAgents 用于学习金融流程拆分与工程组织；FinanceBench 用于学习评测。没有理由因为参考项目采用多 Agent，就立即把我们的控制循环改成多 Agent。

## 本地代码中值得避免的设计

本地 `tradingagents/agents/analysts/fundamentals_analyst.py` 第 189–213 行，提示词要求具体目标价，并禁止“无法确定价位/需要更多信息”。同时要求不编造数据。这些要求在证据不足时存在张力。该观察仅针对当前本地提交，不代表所有版本或整套系统均会产生错误。

我们的研究助手应允许补充检索、部分完成和证据缺失；数值与引用约束由代码验证，不能只靠提示词强调“不得编造”。

本地 `agents/utils/agent_states.py` 保存报告、辩论历史、轮次与工具计数；`graph/setup.py` 构建节点和条件路由。这些可以帮助理解业务状态如何区别于聊天消息，值得教学借鉴。

## 路线选择

| 路线 | 适用目标 | 主要代价 | 本次判断 |
|---|---|---|---|
| 独立开发 TradingAgents 式交易系统 | 专注投资信号、回测与组合研究 | 价格/时点数据、交易成本、回测与收益验证；角色调用和归因复杂 | 与当前金融 Agent 工程目标不够直接，不选为主线 |
| 在 TradingAgents-CN 上二次开发 | 希望快速进入成熟应用并提交特定模块贡献 | 大代码库、来源与贡献区分、版本/许可、理解成本 | 可作为另一项实践；不替代用户要求的独立项目 |
| 独立构建证据驱动的基本面研究 Agent | 工具、检索、财务计算、可靠性、评测和工程解释 | PDF/表格、财务口径和标注仍有难度 | 推荐作为主项目；借鉴设计，保留独立实现与贡献记录 |

这一判断来自任务与能力目标的匹配，不是声称参考项目缺乏证据能力，也不是未经比较宣称创新或行业领先。

## 建议的最终产品

工作名保留 Financial Report Agent，定位可表述为“面向 A 股公司研究的证据驱动金融 Agent”。年报是第一批数据，不把“宁德时代两期四指标”当最终需求。

目标用户：需要形成和核查初步研究底稿的研究助理/初级分析师，仍需访谈验证需求。产品核心问题是减少查找、对表、计算和核查的机械工作，同时显露证据不足。

最终核心任务沿用产品规格的三类：财务变化核查、依据经营披露的解释研究、证据与口径追问。同业两家公司比较作为范围扩展候选，需先通过口径可比性验证，不立即承诺跨行业排序或完整估值。

使用示例：“分析指定公司两期利润与现金流的变化；区分数字变化、公司披露解释和待验证假设；把关键结论定位到原文。”系统应按问题选择工具与补充证据，而非对任何输入都生成同一份模板报告。

必须形成：资料与版本 → 证据和事实 → 计算 → 结论/解释 → 引用 → 验证与缺口的关联。允许每个结论在 CLI 或报告中查看关联记录。run_id、配置和快照贯穿全过程；不要求多 Agent、数据库服务器或 Web 页面才能成立。

## 对齐公开项目颗粒度

| 维度 | 最终必须交付 | 与参考项目关系 |
|---|---|---|
| 任务入口 | 公司/时期/截止日/问题；追问与导出 | 借鉴成熟项目清晰输入和交付 |
| Agent 运行 | 动态工具选择、证据不足时补检、明确结束/部分完成 | 借鉴 Dexter 循环与 TradingAgents 状态 |
| 金融数据 | 一个获取适配器、快照、页码和受支持范围 | 不能只给模型一段人工整理文本 |
| 财务逻辑 | 有单位/口径的事实和公式工具 | 用确定性验证替代纯模型自检 |
| 可观测性 | JSONL 事件、耗时、usage、预算、错误与重放 | 借鉴 Dexter 轨迹与运行信息 |
| 可靠性 | 参数、权限、网络失败、取消、上下文及结果大小限制 | 按实际瓶颈逐步建设 |
| 评测 | 跨公司保留样本、金标准、失败分类、基线对比 | 借鉴 FinanceBench 证据结构，而非照搬答案 |
| 展示 | README、架构、CI、运行命令、示例底稿、验收记录 | 独立使用者可以复现并核查 |

原 3–5 家公司和 40–60 题作为初步验收规模，不作为“项目级”的定义。至少覆盖不同报告格式、一个保留公司、冲突/缺证据场景；真实模型评测与离线工程测试分开，不能只用测试数量证明价值。

与普通聊天比较：固定资料、相同问题和模型，测试无工具基线；与固定工作流比较：同文档、工具、预算条件，测试自适应检索是否改善有证据的任务完成，及增加多少成本。普通聊天的工具访问情况须明确定义，不把具有同等工具的平台当成无工具基线。

新增功能的必要性用失败样例证明：检索召回不足再比较关键词/BM25/向量；需要跨阶段恢复再选状态机/框架；并行独立任务有测量收益再考虑并发或多 Agent。

## 冻结方向前仍要验证的风险

1. 数据：两家不同格式报告能否可靠下载、解析、保留页码；资料权限与版本登记是否可行。
2. 自动化：不提供金标准答案，系统能否提取指定事实并通过口径核查；记录人工干预率。
3. 业务：真实问题是否确实耗费用户检索和核查时间；邀请一名同学试用或先记录个人手工基线。
4. 成本：人民币 20 元预算不因增加时间而自动增加。单次真实任务成本未测量，不承诺全量、多轮、多模型评测可在此预算完成；先做少量测量，再决定运行数或费用调整。

下一步应做规格讨论和最小数据可行性验证，再冻结最终验收阈值与排期。现有底座不需推翻，但不能在验证前承诺自动通用 PDF 抽取或大规模真实模型评测。
