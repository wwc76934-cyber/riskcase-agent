# 用一句话发起调查

这个阶段解决一个具体问题：分析人员知道想查什么，但不想记程序里的检查名称和参数。

例如输入“查金额和新商户”。系统先给出两条待确认检查：

1. 本笔正金额，是否超过此前滚动30天的正金额最大值？
2. 这家商户，在该用户此前滚动30天里有没有出现？

确认这个范围后，程序才查询案例、计算结果、附上证据引用。最终报告还要单独审阅。确认调查范围不等于批准风控规则。

## 模型与代码各做什么

模型只把一句话翻译成“要查哪些项”。它看不到交易金额、交易历史、欺诈标签和标准答案，也没有调查工具。它不算数字，不认定欺诈。

程序把这些项编译成固定查询。例如金额与新商户只需要“本笔交易、30天历史摘要、30天目标商户记录”三次查询。模型不能改变SQL、用户、截止时间、窗口、阈值或样本要求。查询后，代码计算结论并生成报告。

这仍然需要确认：模型可能把“不要查金额”理解错。JSON字段正确，只能说明格式对，不能说明听懂了人话。系统不把格式校验包装成语义正确保证。

| 你说的话 | 系统下一步 |
|---|---|
| 查金额和新商户 | 展示上述两条具体口径，等待确认 |
| 只查频次，不查单笔新高 | 计划只查此前1小时至少4笔这条线索 |
| 帮我看看异常 | 请求明确调查范围，本次任务不取证 |
| 冻结账户 | 标明超出范围，本次任务不取证 |
| 查近48小时频次 | 当前不支持这个窗口，不偷偷改成1小时 |

“需要澄清”的任务在本版停止；明确问题后重新提交，不假装已有完整多轮对话功能。

## 五条检查的意思

- **频次**：此前1小时至少4笔，是本项目实验口径，不是银行通用标准。
- **单笔金额**：比较本笔正金额和此前30天正金额最大值。
- **新商户**：检查此前30天是否出现同一商户ID；新商户本身不等于欺诈。
- **笔数集中度**：比较近7天、近30天各自Top1商户的交易笔数占比。
- **正金额集中度**：同样比较，但用正金额作为分母；不把负金额自行认定为退款。

两个集中度窗口至少各10笔。完整历史、足够样本和正金额分母是不同条件，缺少必要资料就输出资料不足。近7天包含在30天内，不能当作两个独立时期；两个窗口的Top1商户也可能不同。

数据仍是IBM合成交易，币种、时区和标签确认时间未知。源内查询正确，不等于真实支付业务中的判断有效。

## 自己运行一次

在仓库根目录运行，不收费：

```powershell
.\scripts\run_project.ps1 -m app.cli.natural_demo
```

它会创建一个新的运行目录，走完三种路径：支持的范围、含糊问题、越界请求。第一条会模拟调用确认接口，再生成报告并由独立源SQL核验。确认明确标记为 `SIMULATED_CONFIRMATION_NOT_HUMAN_REVIEW`，没有真人审阅，也没有批准金融策略。

这条命令使用离线关键词脚本，适合看数据流，不能证明大模型能力。加 `--live` 才使用已保存的硅基流动凭据并计费。演示使用进程内鉴权HTTP测试客户端；实际双进程服务的启动方法见 [服务指南](SERVICE_GUIDE.md)。

## 接到实际本地服务

向已有 `/jobs` 接口提交以下正文，仍需本地Bearer令牌和新的 `Idempotency-Key`：

```json
{"case_id":"development-467716","task_type":"natural","mode":"offline","question":{"text":"查金额和新商户"}}
```

工作进程处理后，任务进入 `awaiting_plan_confirmation`。读取该任务的 `plan.json` 和 `summary.json`，检查中文口径。向 `/jobs/{id}/confirm-plan` 提交当前 `expected_version`、`result_hash`、`plan_hash` 和 `decision="confirm_plan"`；拒绝则用 `reject_plan`。工作进程下一次运行才取证。取消、旧版本或内容变化的计划不能继续。

结果进入 `awaiting_review` 后，用原来的报告审阅接口。范围确认和报告审阅是两个不同动作，均不批准金融候选。

本地服务使用共享令牌，只能验证调用者持有令牌，不能鉴别人还是脚本，也没有企业人员身份或多级审批。调查模型没有确认接口工具，不能自行确认自己的计划。

## 本轮测什么

80条自建中文问题，40条开发、40条评测，先冻结题目、代码、提示和口径，再分别运行关键词路由和真实模型。主要指标是“是否选对动作，并且选对全部且仅有的检查项”。多查、漏查、格式失败都不能算完全正确。

自动评测会模拟接受每个合法执行计划，故意不拿标准答案修正它，再检查数字。这样可以分别看出“听错需求”和“计算错误”，但不能证明真人能发现所有计划错误。

这些问题由项目作者编写，两部分共享任务类型，案例复用8名合成数据用户；没有外部专家标注或真实分析人员试用。模型得分较高，也只能支持当前题集上的范围理解能力。详见 [本轮阶段结果](NATURAL_STAGE_REPORT.md)。
