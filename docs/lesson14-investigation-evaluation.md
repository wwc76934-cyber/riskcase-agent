## 1. 真实模型这次完成了什么

真实运行目录是 `runs/live-case-v1-d1dde6e08986`。模型通过硅基流动完成 4 次请求、4 次工具查询，最后一次请求用于纠正最终回答的格式。纠正后，结论通过了检查，报告正式生成。

它对同一笔预警查到了这些事实：

| 怀疑 | 工具实际查到 | 可以说什么 |
|---|---|---|
| 此前一小时是否至少 4 笔 | 0 笔，源内覆盖完整 | 不支持这一频次线索 |
| 本笔是否超过过去 30 天正金额最大值 | 本笔 803.34，历史最大 488.48 | 支持这个金额比较线索 |
| 过去 30 天是否未出现该商户 ID | 有 44 笔历史，但该商户 0 笔 | 支持这个“近期未出现”线索 |

这里的金额币种未知，不写成人民币。后两项成立也不表示确认欺诈：一个人去新商户买一件贵东西，也可能完全正常。我们的调查产物是可核对的线索，不能把它当犯罪判断或直接冻结依据。

独立脚本已对照原始事实库，核对 45 条案例投影、4 个工具回执、最终引用和报告。没有打开目标标签库，没有评测 2019 最终测试。这说明报告与本案例事实一致，尚不说明欺诈识别率、调查效率或对其他案例的能力。

本轮按配置较高费率估算 0.073276 元。到本批检查时，三次真实运行共发出 8 次请求，账本累计占用估算 0.209368 元，其中 0.089120 元是首轮未知用量的预留。实际扣费以平台账单为准。本批没有另发真实请求。

## 2. “测试通过”和“模型靠谱”有什么区别

用考试来理解：

- 单条真实冒烟：确认学生能够进考场、读题、交答卷，至少有一次答卷符合要求。
- 程序回归测试：确认考试系统没有把缺题算满分，也没有把错误答案显示成正确。
- 开发任务：我们知道答案，用它们检查流程、找问题、改提示词。
- 保留任务：方案冻结后再用来测能力，不能一边看成绩一边反复改到满意。

本批新增的是第三项的第一小步，同时测试第二项。它没有完成最后的能力考试。用来修格式的这笔预警已经看过多次，必须算开发案例，不能当作新的独立保留案例。

## 3. 我们先放进哪些题

9 个题目都是专门手写的微型数据，不是从 IBM 数据抽出来的真实样本，也不是欺诈标签：

| 场景 | 要抓住的问题 |
|---|---|
| 金额正常、商户见过 | 不能为了发现风险而硬说异常 |
| 金额较大、商户未出现 | 能分别引用两条事实 |
| 一小时内 4 笔 | 能走频次分支，补查一天背景 |
| 只有半小时覆盖 | 不能拿半小时数据证明一小时不频繁 |
| 一小时完整、三十天不完整 | 不同窗口可以有不同资料完整性 |
| 没有历史 | 无法建立金额、商户的比较基准 |
| 当前金额为负 | 不擅自解释成退款，不套用正金额比较 |
| 混入未来、同刻及其他用户记录 | 案例投影必须排除这些记录 |
| 窗口起点和金额恰好相等 | 起点包含，当前排除；等于最大值不算“超过” |

例如，资料只有半小时，其中有 1 笔。不能说一小时只有 1 笔，因为更早半小时没资料。正确输出是 insufficient_evidence，也就是“证据不足”。**承认不知道，是这道题的正确答案。**

## 4. 怎么评分，才能避免自说自话

每道题事先写好期望结论，称为 gold。调查工具只拿案例事实，不拿 gold，也拿不到场景名字和评分结果。

评分器检查：该回答的检查项有没有漏掉，判断是否与预先答案一致，是否新增未知检查项或重复项，以及调查本身有没有通过证据校验。即使某次状态写了 completed_validated，只要漏掉任务要求或结论不对，任务仍不通过。

本版沿用分支式调查合同：频次成立时可以只报告频次并查一天背景；一小时覆盖不足时可以报告缺口并结束。这两题各要求一项，其余七题各要求三项，所以共 23 项要求。这个规则已写在版本化开发配置中，不在看到模型结果后临时降低标准。它衡量这个窄任务合同，不代表全面调查能力。

本轮先用写死的离线客户端跑：9/9 任务通过，23/23 必需项正确，没有提交额外错误项。**这证明任务、工具和评分器能够串起来；不意味着真实大模型取得了 100% 正确率。** 下一步才能逐步把真实模型放到相同任务里，并记录失败、格式纠正和额外查询的代价。

本批为评分与任务构建新增 16 个测试，全仓 260 测试通过。还检查了保存的配置、每份轨迹与案例说明的哈希和汇总计数。

## 5. 你现在可以运行什么

在项目根目录运行，不联网、不需要密钥，也不产生模型费用：

```powershell
.\.venv\Scripts\python.exe -X utf8 -B -m app.cli.evaluate_investigation
```

重点看输出的 `tasks`、`tasks_passed`、`required_checks` 和 `correct_required_checks`。结果写入新的 `runs/investigation-dev-v1-*` 目录，其中保存配置副本、每题 case、轨迹、报告以及 evaluation.json。

本批实测目录是 `runs/investigation-dev-v1-f14dedada88d`，实现提交是 `a91a10dd14181b64c72c28d2319761c95a166950`。

你最需要掌握的一条开发思路是：**先规定任务和正确答案，再看系统能不能完成；失败也保留。** 后续将补真实源中的开发案例、同权限固定流程对照，以及隔离的保留任务，之后再进入候选规则验证。手工任务不能替代这些步骤。
