# 第八批结果：第一次机器学习训练完成

更新：2026-10-16。先读 [第八课：模型怎样学习](lesson08-machine-learning.md)，再查本页实验数字。

## 一句话进度

数据 → 历史特征 → 规则 → **逻辑回归与梯度提升树已实际训练和验证** → 时间稳定性与 PyTorch 实验 → Agent 调查 → 规则验证和交付。

当前树模型比初始规则多找到一些欺诈，但误报很多，训练与验证差距明显。我们已经有可复核的检测起点，还没有可投入现实支付业务的完整 Agent。

## 训练到底做了什么

模型读取训练交易的 14 个线索和训练答案，学习参数；然后只读取验证交易的线索预测分数，评测代码在预测后核对验证答案。调查 Agent 不读答案。

| 项目 | 固定选择 |
|---|---|
| 数据 | IBM TabFormer 合成交易；500 个预先选定用户 ID，完整登记时间内的源内历史 |
| 训练 | 2016～2017 年，841,892 笔，967 笔欺诈标签 |
| 验证 | 2018 年，422,088 笔，683 笔欺诈标签 |
| 最终测试 | 2019 年：本批没有查询记录、生成预测或评测效果；此前样本建设已有总量统计，不宣称从未知道其标签总数 |
| 历史预热 | 2015 年 12 月；当前、同刻、未来交易不计入历史 |
| 模型 | 逻辑回归；直方图梯度提升树，各一个开跑前固定的配置 |
| 类别权重 | 正常约 0.5006，欺诈约 435.3113，只由训练标签计算 |
| 比较 | 同一验证快照、每天 10 笔审核预算、同一并列分数排序方法 |
| 随机种子 / 线程 | 42 / 2；依赖固定于 requirements-ml.txt |
| API | 本批 0 次，本项目累计真实 LLM 调用仍为 0 次 |

配置在 `config/ml-experiment-v1.json`，训练代码提交 `f6a1934`。运行前另写入 frozen-experiment.json，保存参数、输入、软件版本、代码与数据指纹。

模型输入不包含用户编号、交易编号、目标答案或分区标记。逻辑回归的填补、缩放、类别编码只 fit 训练集，随模型一同保存；树模型明确处理类别和未知类别，不把商户类别编号当连续大小关系。

## 相同工作量下的成绩

365 天，每种方法都审核 3,650 笔。表内“查准率”表示这些审核交易中多少标为欺诈；“召回率”表示验证期 683 笔欺诈找到了多少。

| 方法 | 找到欺诈 | 审核中的正常交易 | 查准率 | 召回率 | AP |
|---|---:|---:|---:|---:|---:|
| 金额排序 | 35 | 3,615 | 0.96% | 5.12% | 0.002953 |
| 组合规则 | 40 | 3,610 | 1.10% | 5.86% | 0.005272 |
| 逻辑回归 | 35 | 3,615 | 0.96% | 5.12% | 0.007773 |
| 梯度提升树 | 95 | 3,555 | 2.60% | 13.91% | 0.016483 |

AP 评价整体排序，前 10 笔审核评价每天最有限的名额；逻辑回归的两项表现说明不能用一个指标代替另一个。每天取前 10 笔是日终回放，不能解释成实时拦截能力；也没有给模型临时发更多审核名额。

树模型相对组合规则，净多找到 55 笔；拆开看，它找到了规则未找到的 78 笔，同时漏掉了规则原本找到的 23 笔。并非保留原有 40 笔后无损增加 55 笔，也不能直接把两个名单相加后继续声称审核预算不变。

这是一轮合成数据验证结果，尚无多时间窗口、多种子稳定性、独立最终测试或真实业务结论。

当前 Windows 环境中 joblib 查询物理核心的系统命令不可用，回退到逻辑核心数；警告已保留，训练成功且计算线程通过 threadpoolctl 限制为 2。没有隐藏训练失败，也没有因看到验证分数而重调参数。

## 数据分析发现了什么

**第一个重要发现：训练期和验证期，欺诈标签的渠道分布不同。**

| 渠道 | 训练全部交易 | 训练欺诈 | 验证全部交易 | 验证欺诈 |
|---|---:|---:|---:|---:|
| Chip | 617,040 | 128 | 310,348 | 564 |
| Online | 100,845 | 773 | 50,576 | 28 |
| Swipe | 124,007 | 66 | 61,164 | 91 |

训练的 967 个正例中约 80% 是 Online，验证的 683 个正例中只有约 4% 是 Online。与此同时，各渠道在全部交易中的比例较接近。这是风险分布变化的具体证据，不能只看总体行数正常就跳过。

逻辑回归把 3,412 个审核名额给 Online，只找到 15 笔欺诈；树模型给 Online 2,395 个名额，找到 25 笔，而验证期多数欺诈实际发生在 Chip。它们都值得继续检查渠道依赖。观察尚不能证明模型因果机制，之后用预先记录的渠道特征消融和更早年份的滚动验证检查。

**第二个发现：模型对练习题和下一年的成绩相差很大。** 两个模型都有明显的训练/验证 AP 差距；可能包括过拟合、渠道风险变化以及用户/欺诈模式变化。不能因为训练 AP 很高就宣称检测成功，也不能凭这些汇总数确定唯一原因。

**第三个发现：交易不是彼此独立的考试题。** 训练正例分布于 210 个用户，验证正例仅分布于 64 个用户；验证前 5 个正例最多的用户贡献 109 笔。后续置信区间要考虑按用户或时间成组，而不能把 683 笔交易全当独立事件。

验证中新用户的 605 笔交易没有正例，近期无历史的 4 笔也没有正例。因此当前不能估计这两组的欺诈召回能力。每月树模型捕获数为 7、3、10、5、2、8、6、7、7、5、29、6，不能仅看全年合计而不看月份波动。

## 怎样确认不是报告写错了

全仓 151 个测试通过，覆盖未知类别、缺失值、预处理训练边界、模型保存/加载、禁止本阶段查询最终测试、排序分数校验等；测试不是 151 个实际欺诈案例。

另运行与训练代码分开的复核脚本：

- 对全部 422,088 笔保存的分数，使用另一种排序实现重建每日名单；四组共 14,600 条记录完全一致。
- 不调用 sklearn 的 AP 函数，按分数阈值变化独立累计精确率和召回增量，复算 AP 一致。
- 从独立标签表核对名单 TP/FP/FN 和查准率、召回率。
- 对本地生成且指纹吻合的两个模型重新加载；随机记录加高分记录共 94 笔预测与保存结果完全相同。

这些证明当前代码与产物相互一致，不证明合成源的标签是真实世界事实，也不证明跨环境逐位复现。joblib 只加载自己生成的可信文件；外部文件即使自带哈希，也不能据此当作安全模型加载。
