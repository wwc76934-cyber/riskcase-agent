# V4：完整台账引用与资料缺口反馈

V3修复回归两组均4/6全项通过，24/24事实值正确，5/6决策正确。31+6=37次请求估算1.010104元；截至该批结束项目累计11.959668元。原始结果保留于 `runs/stage5-live-v3/`，没有达到原5/6门槛。

剩余两类问题：资料缺口矛盾被旧的硬错误分支直接拒绝，没有进入已经声明的单次反馈；失败重试一案只引用成功扣款，未提供排除另一次尝试的原文。V4不放宽原评分，也不调整金标准。

改动：

1. 资料缺口、请求材料未列出、仍有必需材料却建议结束等矛盾，统一进入同一 `DraftReviewError` 管道。仍最多一次公开反馈，仍计入6次请求上限，原始草稿保留，不在宿主修改模型答案。
2. 对扣款总数和净额，统一要求引用整份**已绑定、短篇**清算原件，包括覆盖说明、失败尝试和无关流水，便于人工核对排除过程。不是从金标准挑选特定行；所有案件使用同一规则。其他主张仍按相关原文行引用。每段最多8行，多段引用总量仍受现有schema限制；长账单必须另建经过验证的统计/分段方案，本项目不宣称支持任意长度。
3. 同步公开提示和Skill，明确资料缺口优先于排队退款；行文本增加渲染哈希核对，原始正文哈希保持独立，末尾换行不造成伪损坏。

用户输入、6个已观察案例的事实原文/金标准、模型和费用上限保持不变。两组同样接受完整台账引用和单次反馈，不偏袒动态路径。重新冻结后先跑离线和真实MCP验证，再申请新的最多12案/72请求/估算2元批次。旧批次12案已用完，不能复用余额。此轮仍为已观察案例回归，不是新的独立测试。

首次草稿和最终结果分别评分，失败留在分母。沿用原至少5/6全项通过、事实值≥90%、不得错误关闭覆盖缺失、渠道规程对正确的演示门槛；即使通过，也不声称生产价值或总体泛化。
