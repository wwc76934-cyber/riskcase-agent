# 风控 Agent 方向评估

日期：2026-10-14。状态：历史候选比较，未决定转向。用户最新明确不考虑本科项目，不再核实或依赖其资产。基于五份 JD 的最新推荐见 [JD 对齐与反欺诈提案](jd-alignment-and-fraud-proposal.md)；下文原候选优先级已被该提案更新。

## 结论与决选范围

风控有价值，但必须先选金融对象和工作，不宜做笼统的“全能风控 Agent”。

优先候选为风控模型验证与监控调查助手；本科资产可复用时，企业财务风险预警与证据调查助手可能更合适。支付反欺诈/AML 是另一条专业路线，不能用企业财务风险项目声称覆盖。

| 路线 | 目标用户与任务 | 所需数据 | 知识与评测 | 判断 |
|---|---|---|---|---|
| 企业风险监测与调查 | 信用/财务风险分析人员，核查模型或规则预警并补充公开披露证据 | 公司财务、公告、时点、明确风险标签；本科资产待核实 | 财务困境/信用风险、召回与误报、预警提前量、证据支持 | 背景连续性最好；标签和事件时间是难点 |
| 信贷模型验证与监控 | 风控分析/模型验证人员，对比模型、调查表现变化、形成复核包 | 有标签的样本、冻结预测、数据字典；监控需要基线/当前样本与标签成熟信息 | 坏样本定义、样本切分、AUC/KS、校准、分群、漂移、策略权衡 | 可复算、可教学，优先进入决选；最终岗位匹配需 JD |
| 交易反欺诈调查/AML | 风险运营调查人员，从警报定位交易和关系证据 | 交易时序、设备/主体关系、警报与标签 | 不平衡、时间泄漏、告警命中、调查成本、图关系 | 有展示潜力，但当前数据和领域门槛更高 |

表中岗位映射属于业务分析，不是对当前招聘数量、录用概率或企业实际使用的保证。

## 已核查的参考项目

1. [MARVIS-Agent](https://github.com/eddyzzl/marvis-risk-agent)：文档描述数据、特征、建模、验证、策略和监控工作流。直接查看了 [metrics.py](https://github.com/eddyzzl/marvis-risk-agent/blob/main/marvis/feature/metrics.py) 的 KS/AUC/PSI 等实现、[evidence.py](https://github.com/eddyzzl/marvis-risk-agent/blob/main/marvis/orchestrator/evidence.py) 与设计/验收文档；没有安装运行或审计全仓。可借鉴“确定性计算—证据—工作流—人工责任”的设计。其 [能力状态](https://github.com/eddyzzl/marvis-risk-agent/blob/main/docs/capability-status.md) 区分软件、业务和机构生产，源码和本地测试不自动构成生产证明。本轮不复述其自报测试量作为可信度结论。
2. [Microsoft azure-trust-agents](https://github.com/microsoft/azure-trust-agents)：官方黑客松教学仓库，包含客户数据、风险分析、合规报告、警报与可观测性设计。可以学告警生命周期和服务集成；不能因为作者或 README 使用 enterprise-ready 就当作实际银行生产案例，也不必照搬 Azure 多服务依赖。
3. [AML Fraud Network Agent](https://github.com/RahafAba/aml-fraud-agent)：SQL/图查询路由和调查；明确用合成数据，并公开路由与 Cypher 失败。借鉴任务拆分、查询权限和评测；不能以小型合成图上的成功认定真实反洗钱有效。仓库示例金额与境外制度不作为本项目规则依据。
4. [AuditAgent](https://arxiv.org/abs/2510.00156)：论文研究中国上市公司跨年披露中的舞弊证据定位，摘要说明使用执法文书与财报专家标注数据。与企业风险调查有关，但舞弊调查不等于违约预测。本轮仅核查论文摘要，未确认公开代码/数据的可得性、许可或复现效果。
5. [agentic-ai-credit-underwriting](https://github.com/KKAzilen/agentic-ai-credit-underwriting)：明确标注为简单参考实现、风险评分为 mocked。适合理解流程，不适合作为项目级质量上限，更不能复用其模拟评分当真实信用模型。

这些是不同成熟度的设计参考，不是已经验证的生产系统清单。借鉴源码之前另行固定提交与核查许可。

## 优先候选的产品草案：风控模型验证与监控调查助手

目标工作：分析人员拿到模型版本、数据批次和监控异常，确认数字是否可信、表现变化发生在哪些群体、还有什么数据不足，并提交可复核的问题清单与验证包。模型训练和自动审批不是 Agent 的默认职责。

用户输入示例：“检查模型 B 相比模型 A 的表现；如果总体指标正常但某些群体恶化，继续定位。缺少标签或时间定义时先指出，输出验证包，不改变线上策略。”

输入合同：数据集/模型版本、特征字典、正类含义、分数方向、样本标识、预测及标签可得时间、开发/验证角色、参考批次、评价配置。缺少必要条件不能通过猜列名补齐。

运行链路：

1. 登记数据和模型指纹、样本合同，检查重复、连接膨胀、缺失与泄漏风险。
2. 确定性工具计算 AUC、KS、校准、分数分布和预先定义的分群表现；缺标签时仅运行可计算的分布监控。
3. Agent 根据已返回的异常选择允许的后续诊断，不对所有问题执行同一条固定链路。每次诊断记录理由、输入和结果。
4. 以固定分箱和参考样本计算漂移，检查样本构成和标签成熟。关联性诊断不冒充原因证明。
5. 输出实验/监控 JSON、图表、证据引用、缺口、复核建议和工单草稿；由人复核。模型和策略版本保持只读，采纳与部署不是自动执行动作。

风险模型本身可用预先训练的 LR 和一个树模型作候选，先保证冻结、评分和评测正确；避免把自动大规模调参作为亮点。Agent 不直接写任意 Python 或执行 shell；调用有 schema 的诊断工具。

## 数据可行性与重要边界

- [UCI Default of Credit Card Clients](https://archive.ics.uci.edu/dataset/350/default+of+credit+card+clients) 是可研究的候选，官方页有 30,000 样本与 23 个特征。是历史台湾信用卡数据，不代表当前大陆信贷业务；具体许可与字段在下载前确认。
- 它可以练习风险模型验证，不能仅因有多个月还款特征，就宣称有多个申请月份或真实 OOT。若没有独立时间批次，只能报告留出验证，并把合成漂移另标为故障/压力注入。
- 预测分数或模型解释不等于因果解释；没有校准及适用样本验证，不称真实业务违约概率。ST、财务困境、舞弊与信用违约不能互换标签。
- [IBM AML-Data](https://github.com/IBM/AML-Data) 与 [AMLSim](https://github.com/IBM/AMLSim) 为交易/AML 的合成数据参考，不是现实客户交易。可以验证工程与已植入模式，不能直接证明真实反欺诈效果。
- 金标准、保留标签和事后执法结论不得进入需要模拟事前分析的 Agent 输入；先冻结规则和模型，再做独立验收。
- 原有人民币 20 元模型预算有效；本地数值工具不调用 LLM，模型仅接收必要的脱敏结构化摘要。真实调用规模先测成本再决定。

## 企业级要求怎样落成验收

本项目目标可以是“按企业工程要求构建的风控 Agent 原型”。没有机构数据、流量和实际验收时，不称“已达到银行生产级”或“监管合规认证”。

| 要求 | 可实际实现和验证的证据 |
|---|---|
| 输入合同与责任边界 | 标签/时间/分数方向缺失时拒绝误算；人工复核后才能采纳新版本 |
| 数据与产物谱系 | 数据哈希、样本成员、模型/参数/公式版本、run_id、产物引用可复算 |
| 权限和隐私 | 只读输入、资源范围校验；模型出站最小摘要；禁止路径越界与文档指令改权限 |
| 持久工作流 | 任务 API、后台作业、状态存储、检查点、恢复、取消；不以一个长 HTTP 请求代替任务管理 |
| 幂等与恢复 | 重试不重复写产物/工单；进程中断与超时有一致状态；保留失败证据 |
| 数值与模型评测 | 指标与独立实现对照，开发/保留集隔离，分群样本量/不确定性、校准与缺失标签处理 |
| Agent 评测 | 正确选择诊断工具、发现缺口、证据支持、危险动作拦截、完成率、成本时延；对比固定诊断流程 |
| 运行交付 | CI、配置、API/CLI 演示、可观察日志、安装与恢复说明、模型/数据说明和失败记录 |

持久工作流可以先用单服务与轻量状态存储实现，不需要立即引入微服务或多 Agent。权限测试和角色责任可以用测试身份模拟，不宣称完成真实机构 IAM 接入。

## 学习路线随交付展开

1. 输入合同：学坏样本、观察期/表现期、标签成熟和泄漏；能解释哪些数据可用于何时的判断。
2. 指标工具：学 AUC/KS 与校准的区别、分群与样本量；自己计算并解释失败输入。
3. 监控诊断：学 PSI、数据质量和性能变化的区别；没有成熟标签时保留未知。
4. 策略研究：有明确成本/收益参数后才做阈值权衡，不给出普遍适用阈值。
5. Agent 工程：受限工具、计划/执行/验证、状态、幂等、审计、人工复核和评测。

每批仍需用户运行、预测和复述后再推进。风控领域知识要在实现中被测试，不能只在 README 罗列术语。
