# 第 21 课：答案格式错了，可以重交；证据错了，不能放行

## 本次解决什么问题

上批真实模型做了两道商户调查题，都没有发布报告。它们把说明文字和 JSON 混在一起；其中一题还把不完整历史当成完整历史，给出确定结论。

这次给运行程序增加一次受控的格式纠正，并明确“覆盖不足优先于占比比较”。检测模型、数据集、规则回放和审批逻辑都不变。

## 两种错误要分开

**第一种：填表方式错。** 系统要求只交一张固定表格，模型却先写一段说明，再把表格放在后面。这时程序可以说：“请按原要求只提交表格，用已经查到的证据。”

**第二种：表格里的判断错。** 它写成合法 JSON，但把“历史只有 17 天”当成“完整 30 天”，或引用了不存在的证据。此时程序直接拒绝，不自动告诉它正确答案、让它一直改到对。

格式纠正只是一次重新提交机会，不是免检通行证。第二次答案仍然要检查所有数字方向、窗口、样本量和证据。即使格式修好了，错误结论也不能发布。

程序不会直接截取解释文字里的某段 JSON 当作成功答案。这样容易忽略模型在表格外写的冲突结论，也难以明确它最终承诺的是什么。

## “记录够多”和“历史完整”有什么区别

任务要求比较近 7 天和近 30 天。假设数据库只有最近 17 天，但里面已经有 20 笔记录。

- 20 笔：表示当前可见记录不少。
- 17 天：表示还缺了 30 天窗口前面的 13 天。

缺失的 13 天可能有很多交易，加入后占比可能改变。所以“至少 10 笔”的样本条件通过了，仍不能做完整 30 天比较。

本任务要求两窗口都覆盖完整，再检查相应样本量与分母。任何窗口覆盖不足，两个比较结果都必须为“证据不足”。这是本项目的调查合同，不是所有风控业务通用的法定标准。

“证据不足”也不是“没有风险”，只是当前材料不能支持这项判断。

## 这和 Agent 开发有什么关系

模型第一次查工具、提交答案之后，宿主程序还要决定下一步：接受、给一次格式纠正机会，还是拒绝。这是运行控制的一部分，不是只写一个提示词。

本次的具体边界：

1. 初次回答必须保留，包括错误内容、失败类型和请求次数。
2. 只有无法解析成严格 JSON 的格式错误，可以触发一次纠正。合法 JSON 的结构、引用或判断不合规，不触发自动纠正。
3. 初次调查与纠正共用最多 6 次模型请求；剩余次数为零就停止，不重新发一份预算。
4. 纠正请求没有可用工具。模型若仍请求工具，程序拒绝，绝不执行。
5. 模型只得到通用格式说明和此前的工具证据，没有开发题参考答案、欺诈标签或后续回放成绩。
6. 纠正失败、接口失败或用户取消，都保留状态和已有轨迹，不无限重试。

这属于 Harness 的一部分能力：管理模型在什么时候能继续、能花多少、能做什么，以及怎样验收。这里只增加了局部控制，尚未做跨进程自动恢复，不能说完整 Harness 已建成。

## 为什么要记录两份成绩

如果模型首次回答失败，第二次才合规，最终任务可以通过；但首次成绩仍是失败，第二次的费用和请求也要计算。

因此新材料同时保存：

- `first_attempt`：首次答案是否通过，失败在哪里。
- `format_repair`：是否纠正、纠正是否通过。
- `status`：最终是否能发布报告。
- `client_requests`：本次包含纠正在内的全部模型请求数。

不能把“第二次终于成功”写成“首次准确”。而且本次同时调整了覆盖提示和纠正机制，不能仅凭前后两题成绩，推断提升完全来自其中某一项改动。

## 怎么验证

已有密钥会自动读取；下面默认离线，不调用 API：

```powershell
.\.venv\Scripts\python.exe -X utf8 -B -m app.cli.merchant_research
.\.venv\Scripts\python.exe -X utf8 -B -m app.cli.evaluate_merchant
```

第一条跑一个已有 IBM 合成开发案例，第二条跑 8 个手工开发场景。离线策略本来就能输出合规 JSON，通常不会触发纠正；不能用这组离线成绩替代真实模型表现。

故障测试使用 Fake 客户端，刻意模拟格式错、错误结论、企图重新调工具、请求耗尽、接口报错和取消：

```powershell
.\.venv\Scripts\python.exe -X utf8 -B -m pytest -q -p no:cacheprovider tests/test_merchant_development.py
```

真实调用仍是一题一次、每题最多一轮格式纠正；加 `--no-format-repair` 可以禁用该机制。它不会把一次真实失败自动变成重复实验。

最新实测结果见 [项目总进度](PROJECT_STATUS.md)。这些仍是开发验证，不是独立保留任务成绩或真实业务收益。

## 本批实际结果

全仓 398 项程序测试通过，新增 13 项；8 个手工任务离线链和独立源 SQL 复核全部通过。

两道已用开发题的新真实验证：方向相反题首次格式失败，一次纠正后通过；覆盖不足题首次就回答两个指标“证据不足”，无需纠正。首次 1/2、最终 2/2，共 6 次模型请求，估算 0.101572 元。两份报告和首次/最终记录均通过独立核验，失败原稿保留。

覆盖不足题重复执行了相同三查询，所以本批不能声称查询更高效。下一步扩展不同用户的源内预警，检查这套控制是否只在已经练习过的题上有效。原始汇总见 [本批证据](merchant-recovery-v3-results.json)。
