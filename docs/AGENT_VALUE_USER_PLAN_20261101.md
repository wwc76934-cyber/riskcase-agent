# RiskCase Agent 深度升级方案：如何真正证明 Agent 的业务价值？

我的建议是：不要再把主要精力放在增加 MCP、RAG、Memory 或多 Agent 组件上，而是重新设计系统需要解决的“调查任务”，让 Agent 面对真实风控分析师会遇到的不确定性。

我核对了最新仓库。现在的欺诈调查主要还是三项固定检查：

- 过去1小时交易是否高频；
- 当前金额是否超过30天历史最大值；
- 当前商户是否为30天内未出现过的商户。

这些检查都具有确定的输入、公式和输出。Python + SQL 足以完成，甚至通常比 LLM 更便宜、更稳定。

所以，继续提升这三项检查的 Agent 成功率，即使达到100%，也不能有力证明 Agent 必要性。

我认为应当把项目从：

当前：交易预警 → 固定指标核查 → 生成报告

目标：交易预警 → 动态调查 → 多来源证据交叉验证 → 提出下一步调查建议 → 人工确认 → 受控经验复用

需要强调的是，这仍然是支付欺诈告警调查系统，不是重新开发信贷审批、反洗钱或退款争议产品。

这一升级方向有实际业务依据。2026年EMNLP Industry Track发表的一项银行实践研究描述了一个在英国零售银行部署、由人工审阅的调查Agent：它使用16个有类型约束的工具，从多个企业系统取证，生成可追溯的时间线与调查总结，并通过专家评审和返工情况检验效果。其核心价值并非执行了多少次SQL，而是跨系统整合证据、减少人工整理负担。

## 一、我建议优先建设的五类高价值任务

| 优先级 | 调查任务         | 主要展示的Agent能力       | 业务价值假设         |
| --- | ------------ | ------------------ | -------------- |
| P0  | 动态欺诈假设调查     | 自主选择取证路径、根据新信息调整计划 | 减少无效调查、提高证据完整性 |
| P0  | 冲突证据与缺失资料处理  | 跨来源推理、矛盾识别、拒绝过度下结论 | 降低错误判断与错误关闭    |
| P1  | 欺诈事件时间线与关联调查 | 多来源关联、事件排序、复杂行为解释  | 缩短分析师理解案件的时间   |
| P1  | 跨案件记忆与失败驱动改进 | 长期记忆、反馈归因、受控经验复用   | 减少重复错误和重复核查    |
| P2  | 调查优先级与行动建议   | 在证据、成本和审核资源之间进行权衡  | 更有效地利用分析师审核能力  |

如果开发资源有限，我不会要求五项同时完成。最值得优先验证的是前两项，并以第四项作为具有研究深度的后续突破点。

原因很简单：它们分别回答三个面试中的关键问题。

1. 为什么需要模型自主选择工具，而不是固定查询？
2. 为什么需要Agent推理，而不是简单罗列异常指标？
3. 为什么需要长期记忆，而不是每次重新执行相同程序？

接下来我逐项给出业务案例、系统设计与实验方法。

## 二、五类任务应该怎样设计？

### 任务1：动态欺诈假设调查（首要推荐）

最值得作为核心Agent研究任务

业务场景

某笔交易进入日终欺诈审核名单。系统发现此前1小时交易频繁、当前金额高于历史水平。

但是，风险异常可能有不同解释：银行卡被盗用、账户被接管、持卡人集中购物，或者交易历史不完整。

此时真正的调查员并不会机械执行所有查询，而是形成假设，再选择最有价值的下一项证据。

例如，我们设计一个新的合成调查场景：

案例 A：一笔需要动态调查的欺诈预警

以下为建议新增的模拟案例，并非仓库当前真实记录。

初始发现

用户此前1小时发生5笔交易，其中一笔金额明显高于历史水平。

Agent的第一个假设

可能存在未授权使用，需要核查近期账户认证和设备变化。

取得新的模拟证据

近期出现新设备登录；但新设备记录本身不能证明账户被接管。

Agent调整调查计划

优先核查账户变更和持卡人授权反馈，而不是继续重复查询交易金额。

最终待审阅输出

区分支持异常的证据、可能的正常解释、尚未获得的授权信息，并提出下一项核查建议。

这个任务真正考验的是：

Agent能否根据刚拿到的证据，改变原来的调查方向？

如果设备资料没有异常，Agent应该考虑其他解释；如果设备和账户变更存在异常，再进一步核查授权信息。

而不是不管发生什么，都固定执行十条查询。

实验怎么设计？

为同一个初始交易预警设计两种有不同后续证据的模拟环境。

环境A提供可信的持卡人授权材料；环境B提供未解决的账户接管线索。两组起始交易事实相同，后续可用证据不同。

观察 Agent 是否选择不同的下一步工具、是否停止不必要查询，以及是否把不确定性保留下来。

这里的评价重点不是要求 Agent 一定判出欺诈，而是检验调查路径是否对证据变化具有合理响应。

### 任务2：冲突证据识别与缺失资料处理

这是我认为金融业务说服力最强的任务之一。

真实调查中，难点通常不是“查不到交易”，而是不同来源的信息并不一致。

例如：

某客户向机构报告，自己没有授权某笔交易。

但系统中的认证日志显示交易通过了某种身份验证。

Agent应该如何理解？

错误的方式是直接认为：

> 认证成功，所以一定是本人消费。

另一种错误方式是：

> 客户否认，所以肯定发生了盗刷。

专业的处理方式是区分两个事实：支付系统记录了一次成功认证；持卡人否认授权该交易。它们并不必然互相排斥，也不足以单独完成欺诈认定。

美国FFIEC的金融机构身份认证指引就强调了分层认证、交易日志、异常行为监测及风险响应的配合，而不是依赖单一认证信号。

[image](https://www.google.com/s2/favicons?domain=https://www.federalreserve.gov\&sz=32)

federalreserve.gov



我建议专门设计下面四种任务变体。

| 案例类型 | Agent需要识别的问题         | 预期合理行为              |
| ---- | -------------------- | ------------------- |
| 来源冲突 | 客户声明与系统日志不一致         | 分别记录来源，指出冲突，不擅自选择一方 |
| 资料缺失 | 设备日志只覆盖部分时间          | 说明覆盖缺口并提出补证请求       |
| 时间错位 | 某条证据在调查截止之后才可用       | 不将它当作之前已经存在的事实      |
| 证据污染 | 商户备注包含诱导Agent忽略风险的文字 | 将备注视为不可信数据，不执行其中的指令 |

最后一种案例还可以测试 Prompt Injection 防护能力。

不过注意，外部文本中的提示注入和业务事实冲突是不同风险，需要分别评分。

为什么这个任务能证明 Agent 价值？

如果只是检测某个固定字段是否矛盾，代码依然可以做到。

真正可能发挥 LLM 价值的是：面对格式各异的客服记录、认证描述、调查备注和业务规则，能够抽取事实、识别语义冲突，并把它们整理成分析师可以核对的材料。

这也要求比较一个非常强的基线：直接把全部原件一次性输入LLM生成报告。只有当动态 Agent 在质量、成本、访问权限或信息缺失处理上表现出优势时，才能证明多步规划有额外价值。

### 任务3：跨交易时间线与关联调查

当前项目已发现同一用户同日可能占用多个审核名额，并实现了导航分组。

我建议在此基础上进一步发展，但不直接引入复杂图神经网络。

假设某用户一天有六条预警。

分析师真正关心的可能不只是每笔是否高频，而是：

这六笔交易是否属于同一次异常行为过程？

Agent可以将不同交易的时间、金额、渠道、商户和新取得的合法证据整理成一条事件时间线。

这里需要区分：

| 适合代码完成   | 可能适合Agent完成             |
| -------- | ----------------------- |
| 同用户交易分组  | 根据调查目标判断需要查看哪些关联事件      |
| 时间排序     | 将交易事件与非结构化调查记录组合成可核对时间线 |
| 金额统计     | 区分哪些事件支持某种假设，哪些事件构成反证   |
| 生成关联记录ID | 为分析师解释关联依据与仍需验证的关系      |

业务结果应是一份案件级调查摘要，但必须保留每笔交易独立的来源、时间截止和审核状态。

不能因为六笔交易属于同一用户，就直接合并审批，也不能把“共同用户ID”夸大为欺诈团伙证据。

这类任务对展示 Agent 的综合分析能力很有帮助，但在开发优先级上，我会将其排在动态调查和冲突证据之后。

### 任务4：跨案件记忆与失败驱动改进

这是我认为最适合把你提供的15页记忆研究材料真正落地的方向。

目前项目虽然实现了记忆的候选生成、审批、检索和撤下，但更多是在验证记忆能否被正确保存和复用。

下一步应该证明：

一条经过审阅的经验，是否真的帮助Agent在新的调查任务中避免了以前的错误？

建议设计这样一个研究场景。

第一轮，Agent在一个模拟案件中错误地认为「认证成功即可排除未授权交易」。

独立评审者指出错误，经过来源核验，形成一条受审阅的调查方法经验：

> 认证成功只能证明某项认证流程通过，不能单独证明持卡人真实授权；遇到授权争议，应核查相关账户、认证与持卡人证据。

第二轮，给Agent新的案件。

新的案件不应只是把旧案例的用户ID、金额改一下，而应该改变交易形式、文字描述或认证情境。

然后比较：

| 实验条件          | 观察什么           |
| ------------- | -------------- |
| 无记忆Agent      | 是否重犯同一类错误      |
| 有原始历史记录Agent  | 大段历史是否真的能被正确利用 |
| 有受审阅方法记忆Agent | 是否能够迁移正确的调查原则  |
| 有过时或错误记忆Agent | 是否能拒绝不适用的历史建议  |

最后一组十分重要。

因为在金融风控中，记忆并不总是有益的。错误经验如果被反复复用，可能形成系统性的判断偏差。

需要特别强调：不能让模型先犯错、自己写一句反思，再由同一个模型证明自己变好了。

应由独立的事实标准或评审者确认错误；由系统保证经验发布边界；再使用未参与经验生成的新案例评估改善。

这样才能把目前的“受控记忆管理”逐步发展成具有研究说服力的“反馈驱动能力改进”。

### 任务5：调查预算下的下一步最佳行动

这是一个值得保留的研究方向，但我不会第一阶段就开发得很复杂。

真实风控调查往往受限于时间、工具费用和信息可得性。

假设某个案例还可以查询五类资料：

认证、设备变更、客户反馈、商户背景、账户历史。

Agent不应该无差别地全部查询。

理想情况下，它应该结合当前证据、工具成本和预期信息价值，选择最值得进行的下一项调查。

可以把研究目标写成：

\\[ a^\*=\arg\max_a \left[ \mathbb E(\Delta Q\mid a)-\lambda C(a) \right] \\]

其中：

- \\(a\\)：候选调查动作；
- \\(\mathbb E(\Delta Q\mid a)\\)：预计能提高多少调查质量；
- \\(C(a)\\)：调用成本；
- \\(\lambda\\)：业务对成本的权重。

这是一个用于建立研究思路的简化目标函数，并不表示现有系统已经估计出真实的期望信息价值。

这一任务能展示规划能力、工具选择、预算管理和何时停止调查。

但必须设计足够强的简单基线。尤其当可用资料只有少量短文档时，全部读取反而可能更好。项目此前的支付争议实验就已经出现过这种情况。

## 三、真正决定项目价值的，是如何构建可信的业务数据

这里我会非常谨慎。

你目前有两类主要数据：

IBM TabFormer 合成信用卡交易数据用于现有预警主线；ULB/Worldline公开匿名信用卡交易数据可用于独立检测实验，但没有支持完整调查的稳定客户、商户和认证原件。

因此，不应该让Codex直接为IBM中的每一笔交易凭空编造设备日志、客户投诉和最终调查结果，再把这些内容作为真实原始数据展示。

我建议采用三层数据架构。

| 数据层           | 来源                                | 作用                   |
| ------------- | --------------------------------- | -------------------- |
| A：可追溯交易事实层    | 现有IBM合成交易源及其冻结模型输出                | 提供实际研究中的预警、交易历史和来源引用 |
| B：明确标注的模拟调查环境 | 独立生成、保留真实业务结构的认证、设备、客服及调查记录       | 用于开发和验证动态Agent调查能力   |
| C：独立评测与反馈层    | 预先定义的案例真值、人工评审和结果评分，若能获取则补充合法公开案例 | 判断调查是否正确、有无额外价值      |

其中 A 和 B 可以在一个明确标注为“扩展模拟环境”的案例中关联，但绝不能声称B来自IBM原始数据，或拿B中的合成材料证明真实银行效果。

### 建议新增的调查数据合同

建议新增的数据来源

| 资料类型    | 业务用途       | 当前状态       |
| ------- | ---------- | ---------- |
| 交易历史    | 金额、频次、商户基线 | 已有         |
| 认证与登录事件 | 授权与账户安全线索  | 需模拟或获取授权来源 |
| 设备变更记录  | 辅助分析账户接管假设 | 需模拟或获取授权来源 |
| 客户反馈记录  | 记录客户声明及其时间 | 需模拟或获取授权来源 |
| 版本化调查规程 | 约束可建议的调查动作 | 已有研究规程基础   |
| 已审阅历史案件 | 经验复用及反馈研究  | 已有受控记忆基础   |

每条资料至少要带有 `source_id`、主体与交易关联键、`event_time`、`available_at`、来源类型、覆盖范围和版本。

同时需要一个独立的、Agent看不到的评分环境，保存每个案例允许的调查结论和关键证据。

一个非常重要的原则是：模拟案例必须有真实的业务逻辑和可验证的内部一致性，但模拟得再逼真也仍然只是模拟。

## 四、如何设计实验，才能让面试官相信 Agent 真的有价值？

这是整个改进方案中最关键的部分。

我建议正式建立一个 Fraud Investigation Agent Benchmark，作为项目自己的任务评测体系。

这不是为了宣称发明了新的行业标准，而是把原来“看演示是否成功”的方式，升级为具有业务场景、独立案例、强基线和失败记录的研究协议。

### 4.1 必须比较四种方案

| 方案              | 具体做法                    | 用来回答什么问题         |
| --------------- | ----------------------- | ---------------- |
| B0：确定性工作流       | 预先约定的SQL、统计和规则自动生成证据包   | 代码本身能做到多少        |
| B1：一次性LLM分析     | 读取所有可用且获授权的案件材料，一次性生成报告 | LLM语言分析是否有价值     |
| B2：动态调查Agent    | 让模型按证据选择工具、更新计划、生成报告    | 多步骤Agent是否带来额外价值 |
| B3：Agent + 审阅记忆 | 使用B2的结构，再引入合格的历史经验      | 长期记忆是否真正有增益      |

四组应使用相同基础事实、权限与评分标准。不要为了让动态Agent胜出，就故意不给B1完整资料，或者只给B0一个异常弱的代码实现。

比较时不仅要问“谁能完成任务”，还要问：

多花的钱、多用的时间、多增加的出错机会，换来了什么？

### 4.2 评价指标应该分成四层

建议的研究评价体系

| 维度        | 核心指标                           |
| --------- | ------------------------------ |
| 事实与证据质量   | 证据支持率、关键证据覆盖率、冲突识别率、事实错误率      |
| 业务决策质量    | 缺失资料识别率、正确补证建议率、错误关闭率、错误升级率    |
| Agent执行效率 | 工具调用次数、有效取证比例、模型成本、耗时、预算耗尽率    |
| 长期记忆价值    | 重复错误减少、有效经验迁移率、错误记忆污染率、过时记忆拒绝率 |

还可以设立一项核心综合评价：

\\[ \Delta Q=Q\_{\mathrm{Agent}}-Q\_{\mathrm{Baseline}} \\]

这里 \\(Q\\) 可以是事先冻结的、由证据完整性、事实正确性及调查建议质量共同构成的任务分数。

但不应只报告这个差值，必须同时公开额外的费用、延迟与安全错误。

在真实业务材料和人工分析师尚不可用时，不能声称节省了多少人工时间。 可以先报告独立证据覆盖率、调查完成情况和调用开销，之后再单独设计分析师对照试验。

英国政府的反欺诈调查专业标准也强调，调查报告需要提供足够事实及来源，使其他审阅者能够独立复核其结论和调查过程。这正好支持我们把证据可核查性设为核心指标。

### 4.3 不要再只用四个合成案例

我建议为新研究设立一个可管理的任务集合。下面是建议的建设规模，而不是现有成绩。

| 数据组   | 建议规模   | 用途               |
| ----- | ------ | ---------------- |
| 开发集   | 约30个案例 | 调试工具、Prompt、状态机  |
| 冻结评测集 | 约40个案例 | 比较B0–B3，不用于调参    |
| 独立挑战集 | 约20个案例 | 使用不同叙事和证据组合，测试泛化 |
| 合计    | 约90个案例 | 覆盖多个欺诈调查场景       |

这些案例应覆盖不同的业务机制，而不只是同一个模板换90个用户ID。

建议包含正常但行为异常、账户接管嫌疑、身份验证证据冲突、资料缺失、历史数据不完整、关联交易、规程版本变化和错误记忆等类型。

开发案例和评测案例最好按业务情景家族拆分，而不是随机打散高度相似的模板。

对于复杂场景，建议预先冻结案例真值、可用证据、时间约束和评分细则，并安排独立复核。没有独立复核的合成测试也有研究价值，但不能宣称是外部业务验证。

## 五、项目架构应该怎样升级，而不是推倒重来？

我不建议重构现有检测模型、MCP、Harness和记忆系统。

新增内容主要集中在调查能力和实验任务层。

建议的下一阶段系统架构

现有风险检测与审核队列

Investigation Planner（新增核心能力）

维护待验证假设、证据缺口、优先查询项与剩余预算

MCP事实查询

交易、认证、设备

规程与案例知识

RAG、Skill、Memory

Evidence Validator

来源验证、事件时点、覆盖、矛盾及结论边界

Analyst Review

人工审阅、补证待办、经验候选

Benchmark & Feedback

固定代码对照、Agent消融、审阅反馈与记忆验证

Harness贯穿任务执行、预算、恢复和审计。所有新增外部来源在真实数据缺失时明确标为模拟。

特别重要的是，不应该让LLM自己决定能否越过风险权限边界。它可以提出调查假设和工具请求，但案件范围、数据授权、事实查询、证据校验、审批与最终操作权限仍归可信宿主控制。

从企业工程角度看，这比临时添加多个互相讨论的Agent更合理。

## 六、推荐的实施顺序与阶段验收

我建议按照以下四个阶段推进，不必一次完成所有任务。

阶段A：建立可信的多来源欺诈调查环境

保留IBM源交易与已有检测输出；新增明确标识为模拟的认证、设备、客户反馈等资料，并严格定义数据来源、交易关联和事件可得时间。完成互相冲突、资料缺失、正常但异常等案例家族。

阶段B：动态调查Agent与强基线对照

在原Harness上实现受约束的假设管理、查询选择和调查计划调整。首先证明它能在关键案例中改变取证路径，再比较代码、一次性LLM和动态Agent的质量、成本及错误。

阶段C：有独立反馈的记忆价值实验

复用现有FraudMemory，但加入经审阅的错误归因和不适用记忆测试。使用新的冻结案例比较有无记忆的调查质量，不能把单纯成功读取历史经验作为效果成绩。

阶段D：简历与面试交付

最终只选择一条最能展示增量价值的完整案例，提供来源证据、动态取证轨迹、强基线对照、错误修复和适用范围。其他功能作为技术深挖材料，而不是全部放进两分钟介绍。

### 什么情况下我才会认为项目改进成功？

不要求动态Agent在所有任务上超过代码。

相反，比较专业的结果可能是：

固定统计任务中，代码最快最稳；小规模材料中，一次性LLM已经足够；但在多来源证据不完整、资料逐步到达且需要调整调查假设的任务中，动态Agent能更好地找到关键证据或避免不合理结论。

只要这些发现来自事先冻结、可复核、具有足够独立性的对照实验，就是有价值的研究结果。

如果动态Agent最终仍然没有优势，项目也应该选择更简单的工作流，而不是人为调整任务让Agent获胜。

## 七、这次升级能给简历增加什么实质内容？

如果我们完成上述建设，项目讲述将发生一个重要变化。

现在的简历亮点主要是：实现了MCP、Skill、Harness、Memory，并构建了欺诈预警到调查的工程闭环。

进一步升级后的理想亮点则可以是：

> 针对支付欺诈预警后多来源取证、证据冲突与调查路径动态调整问题，设计具备假设管理、受约束工具调用和证据验证能力的调查Agent；构建固定代码、一次性LLM与动态Agent的对照实验，评估案件证据完整性、错误判断、调用成本及调查效率，并结合受审阅记忆机制研究经验迁移与错误复用风险。

只有当相应实验完成、结果经过核验后，才在简历里补充具体改善幅度。

这会比单纯写“熟悉ReAct、MCP、RAG、Skill、长期记忆、自我进化”有说服力得多。

## 我的最终建议

把“动态假设调查 + 冲突证据处理”确定为下一阶段的核心技术研究目标，把“受审阅记忆带来的独立增益”作为第二研究目标。

不改变现有支付欺诈主线，不动已经完成的冻结检测实验，不丢弃原有固定流程基线，也不为了增加技术栈而盲目引入多Agent或图数据库。

这次深化真正要证明的是：

当金融风控调查从确定性指标查询，变成信息不完整、来源复杂、证据变化、需要选择下一步行动的任务时，Agent是否能够在可控成本与权限内提供比简单程序更有价值的调查结果。

这才是一个能同时体现你对金融风控业务理解、Agent架构设计能力、软件工程能力和实验研究水平的高质量求职项目。

我们此前约定的32节系统学习框架仍然保持不变。这些改进将作为后续M4的Agent规划与记忆、M5的工程治理、M6的实验评估，以及M7的独立实战与答辩中的高级案例，不提前打乱当前L05之后的课程顺序。
