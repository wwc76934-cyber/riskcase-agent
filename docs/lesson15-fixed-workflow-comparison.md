# 第十五课：为什么必须让 Agent 和普通代码比一比

本批已经完成固定流程、同案例对照命令、结果复核脚本和回归测试。**真实模型对照尚未执行：当前进程没有上次隐藏输入的密钥。** 之前那一条真实模型成功记录继续保留，没有被重复计算为新任务。

## 1. 为什么要做这一步

假设有人问：“你这个项目为什么要用大模型？写几个查询再填报告不行吗？”

对于目前三类明确的检查，答案确实是：可以。检查一小时是否至少 4 笔、金额是否超过过去最大值、商户是否出现过，都可以用普通代码完成。我们不能为了证明 Agent 有价值，故意把普通代码的对照做差。

所以这批增加一个认真实现的固定流程。它不读取标准答案，也不调用模型，每次直接完成四个步骤：

1. 读目标交易。
2. 查此前一小时。
3. 查此前三十天的金额历史。
4. 查目标商户在三十天历史中的出现次数。

然后按明确规则计算三项判断，经过与 Agent 相同的证据校验，再填入报告。公式与校验共用业务口径，另用事先手工写好的开发答案检查它们；这不是独立实现的金融算法验证。

## 2. 什么叫公平比较

两边读取同一份案例数据库，绑定同一个用户和截止时间。每边各有自己的工具实例、调用计数和证据记录，不能偷用另一边已经查好的结果，也不能读标签或开发答案。

同一个任务使用同一套评分要求。固定流程始终回答三项；现有分支式任务允许在高频成立或一小时覆盖不足时只回答频次项。这来自前一批已定义的任务合同，不是看到比较结果后临时改的。

这也造成一个重要限制：**少查询，同时也少回答，不能直接说效率更高。** 因此结果同时记录任务是否完成、查询次数、提交检查项数量、客户端请求次数和本地耗时。耗时只是本机观察值，没有重复实验，不能当稳定延迟指标。

运行：`runs/comparison-offline-v1-72638e56940c`。

| 比较项 | 固定流程 | 离线脚本分支策略 |
|---|---:|---:|
| 开发任务通过 | 9/9 | 9/9 |
| 工具查询次数 | 36 | 33 |
| 提交的检查项 | 27 | 23 |
| 客户端交互次数 | 0 | 42 |
| 真实模型请求 | 0 | 0 |

右列仍是写好的 Python 策略，不是大模型成绩。42 次客户端交互没有联网，也不计费。两边都使用手工构造的开发数据，不是新的 IBM 数据样本，不涉及 2019 最终测试。

运行材料、逐题答案计数、证据引用和报告均经复核。实现提交 `a94aa16143cc57ae3f8827ab8d693ba372cf6db9`；复核脚本随后在 `1a177d4` 增加真实调用 usage 费用估算检查。新增 14 个测试，全仓 274 测试通过，保留原有 joblib 物理核心识别警告。

目前能够得到的结论是：对这些窄且明确的题目，固定代码已经很强；还没有证据证明 LLM 更好，也没有效率提升结论。它值得作为后续项目的基线留下，不能因为 Agent 比不过就删掉。

## 4. 你需要掌握的风控知识

风控中的“误报”是正常交易被报为风险，“漏报”是欺诈没被发现。这些指标需要对应的欺诈标签。

本批评分的是“调查线索回答是否符合事实”，不计算欺诈误报率或召回率。例如“一小时 4 笔”是真的，也不表示其中任何一笔一定欺诈。把线索准确率说成欺诈识别率，会混淆两个任务。

同样，当前金额为负时，代码只知道一个负数；没有业务说明时不能自行认定它是退款。新商户也只意味着这个 ID 在允许历史中没有出现。金融数据分析的第一步，是把字段能支持的解释说准。

## 5. 你需要掌握的 Agent 知识

固定流程决定顺序，普通代码计算答案。Agent 则由模型根据任务和已有回执提出下一步，程序负责执行、权限、预算与校验。

Agent 额外引入模型成本、格式错误、不必要查询和不稳定性，必须有收益才值得。后续会增加真实源开发案例、不同调查问题和工具失败场景，再比较是否能在满足同样要求的情况下减少无效查询、正确处理资料缺口。

当前只有三个预定义检查，因此还不能声称开放式调查能力。我们将依据失败和比较结果决定扩展什么，不靠增加 Agent 数量来制造复杂度。

## 6. 运行方法

项目根目录运行完整离线对照，不联网、不需要密钥：

```powershell
.\.venv\Scripts\python.exe -X utf8 -B -m app.cli.compare_investigation
```

真实模型对照先只跑一题 `normal_seen`：一个金额未超过历史最大值、且商户见过的普通场景。它用来检查模型会不会把每一笔预警都解释成异常。

```powershell
.\.venv\Scripts\python.exe -X utf8 -B -m app.cli.compare_investigation --live --task-id normal_seen --prompt-key
```

只在本地终端隐藏输入同一个有效密钥，不发到聊天。真实对照每次必须显式选择一个题目，最多 6 次请求，仍使用单轮 1 元、项目 20 元的本地费用估算控制，不是平台硬性扣费上限。固定流程不产生模型费用。

运行完成后，输出 `comparison-live-v1-*` 目录。一次运行完成不表示两边都答对；看 `arms` 中每边的 `tasks_passed`，以及各题 `run_status`。失败和 Ctrl+C 中断都不能算任务通过；已发出请求可能计费。取消后保留费用审计和已完成工具证据，不宣称完整中断前对话已保存。

复核时把目录替换为本次输出：

```powershell
.\.venv\Scripts\python.exe -X utf8 -B -m scripts.verify_comparison --summary runs/你的运行目录/comparison.json
```

这条命令不联网，核对保存的材料、答案、引用、汇总和真实调用时的 usage 估算。它不验证平台账单，也不独立重算每条原始 SQL。固定流程有 0 模型请求，是真正应该保留并解释的成本优势。
