# 第 20 课：把“最近交易集中吗”变成可核查的问题

后续更新：比较方向已明确，8 个手工开发场景的离线控制链与独立 SQL 复核全部通过。两题真实验证均被拒绝：都加了不允许的文字，“覆盖不完整”题还忽略资料不足。全仓 385 测试通过不代表模型任务通过。完整记录见 [项目总进度](PROJECT_STATUS.md)；下文保留首批结果和教学例子。

## 这一步在完整项目里的位置

我们的主项目仍是支付反欺诈调查与规则验证工作台。检测模型先把需要关注的交易排进审核队列；调查 Agent 再查询相关事实，帮助分析人员理解这条预警。它不负责冻结账户，也不凭一句模型判断认定欺诈。

过去的调查主要查三件事：最近是否频繁交易、当前金额是否超过历史正金额最大值、目标商户是否在历史出现。这一批补第四类能力：回答一个明确的商户分布问题。

**输入：一条已经绑定的开发预警，以及“比较近 7 天和近 30 天的商户集中程度”。输出：两个窗口的准确统计、比较结论、证据编号与资料缺口。**

当前支持的是参数明确的问题，不是任意自然语言问答。短/长窗口可从 24、168、720 小时选择，短窗口必须小于长窗口。默认每个指标至少需要 10 条相关记录，这只是避免用极少样本下结论的实验约定，没有经过业务校准。

## 先讲清楚“集中”是什么意思

想象某用户最近有 5 笔记录：

| 商户 | 金额 |
|---|---:|
| A | 100 |
| A | 100 |
| B | 50 |
| B | -900 |
| B | 0 |

按记录数看，B 有 3 笔，占全部 5 笔的 60%。按正金额看，A 有 200，占正金额总和 250 的 80%。两种算法回答的是不同问题。

本工具明确规定：笔数占比包含正、负和零金额记录；正金额占比只计算大于零的金额。负金额和零金额另外列出。我们不知道负金额对应的真实业务含义，不能自行称它为退款。

**分母决定你究竟在说什么。** 如果把负金额直接加进金额分母，示例总额变成负数，得到的份额就无法表达这里要研究的正金额分布。我们不是悄悄删掉这些记录，而是明确分开统计。

Top1 指“当前窗口里占比最大的商户”，不保证两个窗口的第一名是同一商户。商户 ID 也不一定对应一家物理门店。

## 当前开发预警实际查到了什么

在此前已经使用过的同一条 IBM 合成开发预警上，目标之前有 44 条近 30 天记录。新的查询得到：

| 项目 | 近 7 天 | 近 30 天 |
|---|---:|---:|
| 历史记录 | 16 | 44 |
| 商户 ID 数 | 10 | 25 |
| 按记录数 Top1 占比 | 4/16 = 25.00% | 7/44 = 15.91% |
| 正金额记录 | 14 | 39 |
| 按正金额 Top1 占比 | 19222/73448 = 26.17% | 48848/267347 = 18.27% |
| 负金额记录 | 2 | 5 |

金额分子和分母使用相同的源单位，所以相除不需要知道币种。系统不会把未知币种写成人民币。

可以说：两个口径的短窗口 Top1 占比都更高。**不能直接说：此人正在欺诈。** 正常用户也可能最近只去少数商户。还要结合更多背景、反证和真实业务验证。

近 7 天包含在近 30 天里面，这不是两个互不重叠的时期。因此这里是“短窗口相对长窗口”的描述，不是“本期比上期”的环比，更不是统计显著性结论。

## Agent 到底做了什么，代码又做了什么

1. 主程序先锁定用户和预警时间，给 Agent 一份不含标签的案例。目标交易、未来交易、同一时刻其他交易、其他用户不进入历史统计。
2. Agent 读取目标，然后调用商户分布工具查询两个窗口。此任务只开放这两个工具，不能自己写 SQL 或改用户 ID。
3. 工具遍历完整的允许历史，计算各商户笔数和正金额总和，返回总计、前三名预览、窗口完整性和证据编号。前三名只是展示，分母使用全量允许记录。
4. 模型提交结构化答案：两个占比是更高、更低、相同，还是证据不足，并附两个窗口的证据编号。
5. 主程序重新比较准确的整数比例，检查窗口、样本量和引用。模型说错、编证据、增加欺诈结论，答案就不能通过。
6. 通过后由代码把已核查事实写成报告。另一个核验程序直接查询原始事实库，独立重算聚合并核对案例和报告。

这里延续课程的核心循环：**模型请求工具 → 程序实际执行 → 结果回到消息历史 → 模型继续 → 程序验收答案**。工具输出不是一句模型想象出来的 Observation，而是实际数据查询的结果。

离线模式使用预设策略客户端，只验证这条链能否工作。它不代表大模型有调查能力。真实模式才会调用已配置的硅基流动模型，仍使用原来的预算和请求上限。

本批实际真实调用了 2 次，估算 0.035140 元，失败材料保存在 `runs/merchant-research-live-v1-1410b210dc4c`。模型正确查询了三个工具结果，却把 25% 相对 15.91% 回答成“下降”。它还在 JSON 前写了说明，首先被严格格式检查拒绝；事后检查说明发现了方向错误。即使仅提交其中的 JSON，已有结论核验也会拒绝这个错误方向，测试覆盖了这种情况。系统没有发布真实模型报告，也没有重试到成功。

离线材料位于 `runs/merchant-research-offline-v1-5b010bf470be`，独立 SQL 复核通过。离线成功和真实失败都要保留。下一批要明确告诉模型“短窗口数值大于长窗口就填 increased”，配合方向相反、相等和资料不足的开发任务一起验证；不能只围绕这条案例改到通过后宣布能力成熟。

这一题的查询路径很固定，普通程序也能完成。新增工具扩大了系统可回答的问题，但单题跑通不证明 Agent 比固定流程更高效。后面要在不同任务、缺口与反证场景上比较。

## 怎么自己验证

在项目根目录运行，默认离线，不需要输入密钥：

```powershell
.\.venv\Scripts\python.exe -X utf8 -B -m app.cli.merchant_research
```

输出中的 `output_directory` 是本次材料目录，里面有 `report.md`、`question.json`、`trace.json` 和 `summary.json`。用该目录的 summary 路径复核：

```powershell
.\.venv\Scripts\python.exe -X utf8 -B -m scripts.verify_merchant_research --summary runs/本次目录名/summary.json
```

成功会输出 `source_sql_verified`，表示已与固定原始事实库的独立 SQL 聚合一致；不是证明合成数据符合真实业务。

如需真实模型调用，在第一条命令末尾加 `--live`。程序沿用已经保存的项目凭据，无须每次填写。它有实际 API 费用；本批只做一次有限请求的开发冒烟验证，不自动反复调整到成功。
