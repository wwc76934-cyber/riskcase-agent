# G2-A 阶段验收：源内多用户调查与三组对照

验收日期：2026-10-21。阶段结论：**完成源内商户调查的冻结评测与工程验收；没有证明 Agent 优于确定性代码。** 原 V1 尚未全部完成。

后续进度：G3-A 容量实验也已完成，最新入口见 [容量阶段验收](CAPACITY_STAGE_REPORT.md)；下文保留 G2-A 的实验与当时安排。

## 这次交付了什么

从已冻结的树模型预警队列选出 12 名不同用户，每人一个预警、两个窗口问题，共 24 个任务。源记录来自 IBM TabFormer 合成数据，不是手工编写的题目，也不是现实账户数据。此前反复使用的用户 38 已排除。

问题分别是：近 7 天相对近 30 天，以及近 1 天相对近 7 天，Top1 商户笔数占比与正金额占比是更高、更低、相等，还是证据不足。最低相关记录数固定为 10，仍是未经业务校准的实验策略。

每题执行三组：

1. **固定脚本流程**：预定三项查询，按确定性逻辑计算，不调用真实模型。虽然复用了课程控制循环，客户端完全是写定策略，不作为 AI 能力成绩。
2. **固定证据模型**：宿主先查好相同三项证据，真实模型只作结构化总结，不能执行工具。
3. **工具型 Agent**：真实模型选择并调用允许的工具，再提交答案；最多一次格式纠正，总请求上限 6 次，所有结论仍经代码核验。

三组用同样的预警、截止时间、窗口、样本策略、统计定义和报告校验。两种模型模式的查询控制不同，这是实验变量；不把相同事实输入误称为相同执行路径。

12 个目标预警的事件日期从 2018-01-03 到 2018-07-28，不覆盖整年所有业务季节。

## 怎样冻结和隔离

- 只从 2018 年冻结预警队列选取，每名用户选择队列中的最早预警，再按固定种子的用户哈希排序。选择不读取验证欺诈标签、不按结果挑成功案例。
- 前 6 名用户组成开发部分，后 6 名组成评测部分，各 12 个任务，用户互不重叠。两个任务共享一个预警历史，因此不能当作 24 个独立用户。
- 在所有真实调用之前保存任务、案例、独立 SQL 参考、调用政策和 14 份执行代码的哈希；运行时检查，变化即拒绝继续。合同 SHA-256：`4679dbfe21d20b1f9898d6462b36be8d18804ea3938d410f3f84b1a641c3892e`。
- 本次开发与评测批次并行执行，均使用预先冻结的同一代码与提示，没有根据开发答案调参后再打开评测。评测隔离是任务用户隔离，不是检测器训练用户隔离，也不是外部数据验证。
- 没有进行 2019 年检测最终测试。参考答案是宿主端 SQL 对描述性统计问题的计算，不是欺诈标签，不提供给模型。

时长原始记录在 JSON 中，包含进程启动、哈希和 SQL 复核，并受并行本地任务影响；不作为生产服务延迟或用户节省时间的证据。

## 失败和数据分析

11 个失败全部来自固定证据模型：事后按固定参考检查，8 个涉及忽略样本量不足，另 3 个涉及比较或引用合同错误。没有用参考答案反馈后重跑。逐题错误字段与材料指纹见 [原始汇总](source-merchant-stage-v1-results.json)。这些诊断是事后分析，不改变原成绩。

开发参考答案组合：1 题两个占比都较低，5 题都较高，6 题都证据不足。评测部分：4 题都较高，1 题都较低，1 题笔数相等而正金额较低，6 题都证据不足。

因此不能只看总通过率，还要看不同情况能否处理。源内案例的窗口覆盖均完整，本批“证据不足”主要来自样本量策略，并没有充分检验数据入库延迟和覆盖缺口。此前的手工缺口题仍有独立用途，不能被这批源内任务替代。

## 重复查询、预算与恢复

新增按不可变案例隔离的查询缓存。同一请求重复调用可复用相同证据，但仍消耗工具尝试预算；失败查询不缓存，返回内容使用副本，不能修改缓存或跨案例共享。

故障测试验证了缓存、权限和预算。这次真实批次缓存命中为 0，所以没有实际测得缓存节省收益，也没有 Agent 查询节省。保留尝试数和执行数两个指标，避免夸大。

批处理在发请求前先写执行回执，完成每组后原子保存结果。重启时跳过所有已记录单元，包括失败或中断单元，不自动重试付费工作。处理中断的单元会保持不完整/费用不确定，验收程序不允许宣称阶段完成。这是批处理防重复机制，不是通用任务服务的跨进程自动恢复。

模型网络调用依然沿用硅基流动 `Pro/zai-org/GLM-5.1`、项目 20 元估算上限、每运行 1 元和最多 6 请求。没有复制、打印密钥，使用已有保存凭据。

## 运行和复核

环境检查发现原虚拟环境启动器无法调用其基础 Python。本批新增兼容入口：先检查项目解释器，无法启动时使用桌面已有的 Python 3.12 运行时和原 3.12 依赖，只在子进程设置依赖路径，不覆盖原环境、不重装包。它是本机兼容方案，不是干净环境安装验证。

在项目根目录，以下命令不调用模型，复核已有结果：

```powershell
.\scripts\run_project.ps1 -m scripts.verify_merchant_benchmark --pack runs/source-merchant-stage-v1 --output runs/source-merchant-stage-v1/live-development
.\scripts\run_project.ps1 -m scripts.verify_merchant_benchmark --pack runs/source-merchant-stage-v1 --output runs/source-merchant-stage-v1/live-evaluation
```

全仓测试：

```powershell
.\scripts\run_project.ps1 -m pytest -q -p no:cacheprovider
```

重新做实验时必须使用新的不存在目录；不能覆盖本阶段材料：

```powershell
.\scripts\run_project.ps1 -m app.cli.merchant_benchmark build --pack runs/source-merchant-new
.\scripts\run_project.ps1 -m app.cli.merchant_benchmark run --pack runs/source-merchant-new --output runs/source-merchant-new/offline-development --split development
```

不加 `--live` 时是离线控制链，不代表模型能力。真实批次需显式加 `--live`，有实际 API 费用；已有回执不会重复调用。合同中任何执行代码或政策发生变化，旧冻结实验拒绝运行，需要新建合同，不能悄悄覆盖原结果。

本地原始数据和 runs 不纳入 Git。仓库保存汇总、来源指纹和派生示例；新机器需要先准备已有数据/模型快照，尚不具备无前提的一键复现。

## 对项目方向的决定

本阶段不再通过加大模型调用来改善确定性比例比较。该任务普通代码已经能准确完成，金融数字与样本资格继续由代码负责。

Agent 应在调查任务选择、跨步骤查证、反证与缺口整理、证据约束的规则提议中接受价值验证。现阶段没有证明其减少人工工作或提高真实欺诈识别率；也不因本次最终通过就引入多 Agent、向量库或交易处置。

下一大阶段优先进入 **审核容量约束下的规则验证**：把“新增抓到多少、增加多少正常审核”改为相同审核预算的对照，冻结实验与人工审阅关联；随后补混合调查问题、服务接口、恢复与 CI。数据外部适用性仍按当前优先级后置，结项前必须明确说明。
