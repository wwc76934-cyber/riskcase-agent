# 第十六课：从解释一笔交易，走向检验一条规则

这一批没有更换项目方向。仍然是支付反欺诈调查与规则验证工作台：G2 的真实多任务对照尚待继续，本批先完成 G3 中可独立建设的候选规则验证器。不能把验证器完成说成 Agent 业务闭环已完成。

## 1. 为什么这一步更接近实际工作

一笔交易金额较大，商户近期没出现过，可以形成一个怀疑。但分析师还需要回答：“把这条怀疑变成规则之后，能多找到什么，又会多打扰多少正常交易？”

本批把这个问题变成可运行实验：

`候选规则 → 检查规则是否合法 → 保存本版规则 → 在开发历史回放 → 与已有审核名单去重 → 输出新增捕获和新增误报`

暂时由我们手工写规则，后面再接模型提议与工具调用。这样不会把“模型提出了什么”和“程序到底算对没有”混在一起。

Agent 的预期价值仍待证实：根据分析师的问题选择查询、整理证据、提出符合限制的候选并读取验证结果。计算、权限与规则是否采纳依然由明确程序和人工负责。不是让模型凭感觉给风险评分。

## 2. 这次具体试了哪条规则

同时满足下面四项才命中：

- 当前金额大于 329.90 个源单位，即整数金额字段大于 32990。
- 此前三十天的源内历史覆盖完整。
- 用户确实有此前三十天历史。
- 该商户 ID 在这些历史中未出现。

32990 沿用早期训练集正金额第 99 百分位阈值，没有根据这次标签搜索新阈值。币种仍未知，不能写成 329.90 元。

“大额 + 新商户”这一组合是看过开发期调查后手工提出的假设，不是预先登记的独立验证。不能因为阈值来自训练集，就把整个实验称为没有开发选择偏差。

规则用一张受限的 JSON 表描述：字段必须在白名单，比较只允许大于、大于等于、等于，阈值必须是有界整数，最多四个 AND 条件。不能填欺诈标签、SQL 或 Python 代码。这个小语言称为 DSL，理解成“我们规定好能填哪些格子的规则表”即可。

## 3. 实际回放结果

数据仍是 IBM TabFormer 的合成交易，复用冻结特征和标签；不是新取得的真实支付数据。只回放 2018 开发期的 422,088 笔，其中欺诈标签 683 笔。2019 最终测试没有用于本批评估或调参。

已有基线是冻结树模型每天前 10 笔审核名单，共 3,650 笔。结果如下：

| 审核范围 | 审核笔数 | 欺诈标签笔数 | 正常标签笔数 |
|---|---:|---:|---:|
| 已有模型名单 | 3,650 | 95 | 3,555 |
| 候选规则全部命中 | 3,078 | 38 | 3,040 |
| 规则相对已有名单新增 | 2,885 | 22 | 2,863 |
| 已有名单与规则取并集 | 6,535 | 117 | 6,418 |

规则与已有名单重叠 193 笔，所以不能把规则命中的 38 笔欺诈都算新增。真正新增只有 22 笔。

新增审核命中率为 `22 / 2885 ≈ 0.76%`，意味着新增审核中绝大部分是正常标签交易。已有名单命中率约 2.60%，合并后降至约 1.79%。这些都是当前样本结果，不是上线预计效果。

**这个结果没有提供采纳规则的理由。** 多找到一些欺诈，同时大幅增加审核量，未必划算。没有真实损失、处置成本和业务约束，不能计算收益金额，更不能声称降低了损失。

这里采取“在原名单之外追加审核”，并集不再受每天 10 笔总量限制。因此不能把 95→117 写成“同样审核预算下识别能力提升”。将来如果总审核量固定，必须重新做名单竞争与排序实验。

## 4. 怎么确认这些数字不是程序自己说了算

主程序逐笔用 Python 判断；另外的复核脚本用 SQL 重新计算候选、重叠、并集和新增，再比较报告。422,088 笔范围及新增 22/2863 均已复核通过。

先保存 frozen-candidate，再由独立评测代码打开标签；候选匹配函数只使用事实特征。调查 Agent 没有读取标签的工具。标签确认时点仍未知，所以它是回顾性事件时间实验，不能包装成已验证的实时回放。

本批新增凭据相关 11 个测试、规则相关 16 个测试，全仓 301 测试通过。原有 joblib 物理核心识别警告仍保留，回退使用逻辑核心。

实测目录：`runs/candidate-replay-v1-aa102b8bbb61`。规则实现提交 `cf3ccf2`；SQL 复核提交 `9ee9c42`。报告 SHA-256：`1429e169ddf7bf20cff24c93d335462b0c28d35a5858d1b812f5a7604e3c9def`。

可自己复跑，不需要密钥、不计 API 费：

```powershell
.\.venv\Scripts\python.exe -X utf8 -B -m app.cli.replay_candidate
.\.venv\Scripts\python.exe -X utf8 -B -m scripts.verify_candidate_replay --report runs/candidate-replay-v1-aa102b8bbb61/report.json
```

第一条创建新目录；第二条复核本批已有目录。复核新运行时替换路径即可。当前候选没有人工批准、没有部署、没有真实交易操作。

## 5. 密钥以后不用逐次输入

新增 Windows 凭据管理器入口，固定条目是 `RiskCaseAgent/SiliconFlow`。客户端优先使用当前进程的 SILICONFLOW_API_KEY，否则读取这个专用条目；显式 --prompt-key 仍是只在内存使用的选项。

此前隐藏输入的密钥没有保留，因此无法自动迁移。**只需在普通本地 PowerShell 完成一次初始化：**

```powershell
.\.venv\Scripts\python.exe -X utf8 -B -m app.cli.credentials --set
```

隐藏输入后按回车，保存于 Windows 当前用户、当前电脑的凭据存储，不写入仓库或运行日志。之后可以直接运行：

```powershell
.\.venv\Scripts\python.exe -X utf8 -B -m app.cli.compare_investigation --live --task-id normal_seen
```

检查是否保存只输出状态，不显示密钥：

```powershell
.\.venv\Scripts\python.exe -X utf8 -B -m app.cli.credentials --status
```

需要替换时重新 --set；删除本项目条目用 --delete，不操作其他条目。实现依据微软的 [CREDENTIALW](https://learn.microsoft.com/en-us/windows/win32/api/wincred/ns-wincred-credentialw) 和 [CredWriteW](https://learn.microsoft.com/en-us/windows/win32/api/wincred/nf-wincred-credwritew)。它提供用户范围的凭据持久化，不是同一用户下恶意进程的隔离系统。

本批在受限执行环境读取遇到 Windows 错误 5；以当前用户权限只检查本项目条目后，确认尚未配置。凭据读写流程使用内存假实现测试，没有往真实凭据存储写入测试密钥；真实保存与自动读取将在初始化后核验。后续助手读取该条目可能需要使用当前用户权限执行，不能把受限环境的拒绝误判成密钥无效。

本批没有新增真实 API 请求，已知累计仍为 8 次；原有账本占用估算 0.209368 元含一笔未知费用预留，平台账单才是实际消费依据。

## 6. 下一步要接通什么

先核验持久凭据与未完成的真实开发任务对照，再让模型在受限字段内表达候选意图、调用验证器、根据新增误报解释取舍。验证器不会因为模型推荐就批准规则。此后补版本化人工审阅、更多任务与保留评测，仍按原项目目标推进。
