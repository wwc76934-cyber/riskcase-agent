# PRD｜RiskCase Detection V2：LLM语义增强与半监督时序欺诈检测

**版本：** V1.0  
**日期：** 2026-11-01  
**状态：** 批准启动分阶段研究，不批准直接替换现有检测器  
**参考论文：** 徐佳铭、朱香玉，《SLE-GFD：大语言模型增强的半监督信用卡欺诈检测方法》，《计算机与网络》，2026，52(4)：387–396。

## 1. 项目背景与目标

### 1.1 现有系统

RiskCase当前是一套面向支付风险分析师的事后批量欺诈告警与智能调查研究系统。

现有检测系统使用IBM TabFormer合成信用卡交易数据，构建严格历史特征，使用强树模型、PyTorch残差网络等进行风险排序。

当前已冻结的2019年时间留出实验，在每日10笔交易审核容量下，三种子残差网络集成捕获99个源正标签，匹配强树捕获94个。两者差异未形成可靠优势结论。

系统下游已经接通调查Agent、MCP工具、Skill、Harness、Memory及人工审阅。

### 1.2 本次目标

在不改变现有业务定位、不破坏已有实验和下游Agent的前提下，研究：

**目标A：** 预训练LLM的金融类别语义表示能否提升交易风险排序效果？

**目标B：** 严格历史时序图能否补充现有统计特征未能捕获的行为关系？

**目标C：** 在标签稀缺条件下，半监督一致性学习能否提高检测效果及稳定性？

最终希望形成一套可复现的LLM增强检测候选模型，并通过消融实验证明各组件的独立贡献。

这是研究目标，不预设结果一定优于现有模型。

### 1.3 非目标

- 不直接替换已发布的神经检测器。
- 不修改下游调查Agent的决策或记忆逻辑。
- 不让生成式LLM逐笔直接判定欺诈。
- 不把模型分数直接解释为真实欺诈概率。
- 不从LLM生成已确认欺诈标签。
- 不改写已有2018/2019实验结果。
- 不把已经观察过的2019数据重新声明为全新独立测试。
- 不宣称完整复现论文，除非所有必要实现细节、数据与实验条件均得到核实。

## 2. 技术方案

采用逐步推进的架构：

`原始交易 → 时点特征 → 金融类别语义编码 → 可选时序图 → 检测模型 → 风险分数 → 日审核队列`

### 2.1 模块A：LLM金融语义特征增强（最高优先级）

首先对现有交易数据开展字段审计。

重点候选字段：

- MCC：商户类别码。
- Channel：交易渠道。
- 经确认有业务含义且在相应时点可得的其他类别字段。

必须审查各字段的语义真实性、可得时间、缺失情况、取值数量与来源。

不得将数字商户ID自动解释为真实商户名称、经营状况或信用风险；不得把未知币种、城市或国家含义强加给原始记录。

#### 语义编码方案

优先使用可信来源的MCC类别定义，构建确定性文本模板，例如：

`Merchant category: [verified MCC description]. Transaction channel: [channel].`

其中类别释义必须来自经过审计的来源；未知值明确标记unknown。

使用预训练文本Embedding模型生成类别语义向量，作为检测模型的附加特征。

初始候选：

- Qwen3-Embedding-0.6B；
- 资源不足时采用较小、许可适合的文本嵌入基线；
- 4B/8B只作为有证据支持后才考虑的规模对照。

模型版本、原始文本、tokenizer、输出维度、缓存键、生成时间与来源哈希必须记录。

优先对**唯一且合法的类别文本组合**离线编码和缓存，避免对海量重复交易逐条调用模型。

初版不进行Embedding模型微调。

#### 必须提供的对照

B0：原有数值特征 + 现有类别编码。

B1：相同特征 + 普通可训练类别Embedding。

B2：相同特征 + 冻结的预训练文本语义Embedding。

B3：B2基础上增加合适的可训练投影或受限融合机制。

B0与B1用于确认类别信息本身的价值；B1与B2才是研究LLM预训练语义是否带来额外增益的重要比较。

各方案必须控制数值输入、训练数据、评测窗口和主要训练预算，记录参数量与运行成本。

不得采用去掉全部类别字段的模型作为唯一的“无LLM”基线。

### 2.2 模块B：严格历史时序图（满足准入后启动）

参考SLE-GFD的时序交易图和TGAT思想。

每笔交易可作为节点：

\[
G=(V,E)
\]

优先构建有明确业务含义的历史边：

1. 同一用户或同一用户-卡组合的历史交易关系；
2. 当前交易与前K笔可观察历史交易之间的时序边；
3. 经实验证明必要、且不引入未来信息的其他关系。

所有消息传播必须遵守交易时点：

\[
t_{\text{neighbor}}<t_{\text{target}}
\]

同一时间戳的交易不得因为文件顺序不同而互相提供未来信息。

原始Card必须使用用户内的联合身份，避免不同用户的相同卡编号被错误连接。

禁止将整个未来交易图预先交给模型，再通过mask声称已经避免泄露。

对跨用户的类别关系边必须格外谨慎：仅共享MCC不意味着交易存在真实实体关联，而且容易形成巨大邻居集合与无意义连接。

初始每节点历史邻居上限K设为可配置；论文中的K=6可作为对照起点，但不直接视为已验证最优值。

优先完成轻量级历史图或序列模型，再决定是否实现完整TGAT及门控残差。

必须报告：建图耗时、边数量、内存、训练时间、推理延迟和设备要求。

### 2.3 模块C：半监督一致性学习

参考论文：

\[
L=L_{\mathrm{sup}}+\lambda L_{\mathrm{cons}}
\]

其中：

- 监督损失可采用类别均衡Focal Loss；
- 一致性损失比较同一历史样本在两种合法扰动下的预测分布；
- 对无标签样本使用一致性学习；
- \(\lambda\) 控制两部分损失权重。

需要分别比较：

1. 普通BCE或现有加权BCE；
2. Focal Loss；
3. 类均衡Focal Loss；
4. 监督损失 + 一致性约束；
5. 语义增强 + 一致性约束。

模拟标签稀缺时，仅对训练期样本实施预先冻结的标签mask，例如5%、10%、20%、100%可用标签比例。

抽样方案应在训练期内固定，保留正负类覆盖并报告实际标签数量。不得通过未来测试标签进行类别选择。

**硬性限制：2018开发样本、2019历史评测样本不得作为新模型的一致性训练数据。**

不要复制论文中“测试节点作为无标签节点参与训练”的传导式做法来证明我们系统的时间外推能力。

任何真正尚未确认标签的样本，也必须先经过特征可用性与时间边界审计。

## 3. 数据要求

### 3.1 主要研究数据

IBM TabFormer固定来源。

沿用项目已有的2016—2017训练期、2018开发期及2019历史评测期。

继续使用已验证的数据合同、用户身份、物理交易ID、来源指纹及标签隔离机制。

现有模型特征和实际源码中MCC、channel的具体口径，以仓库核验结果为准。

### 3.2 外部匿名数据

ULB/Worldline公开匿名交易数据已经完成独立检测对照。

但该数据以PCA特征为主，缺少能可靠还原为商户类别语义的原始字段。

因此：

**不得为该数据伪造自然语言交易描述。**

可以用它研究半监督损失和普通模型训练，但不能强行作为MCC语义增强的主要证据。

### 3.3 数据隔离要求

数据必须区分：

- 训练特征；
- 训练标签；
- 开发期特征和评分；
- 历史最终评测特征和标签；
- 无标签训练样本；
- 独立于模型输出的事实及来源元数据。

预处理参数只能依据允许的训练数据拟合。

只允许合法可用的历史交易进入模型的历史图邻域。

模型不得读取下游调查报告、Agent记忆、人工审阅建议或未来欺诈标签作为新特征。

## 4. 研究实验设计

### 4.1 分阶段实验

**实验E1：类别语义是否有效**

原残差基线 vs 普通类别Embedding vs 预训练LLM Embedding。

只改变类别编码相关模块。

**实验E2：语义与历史结构是否互补**

普通残差模型、轻量历史序列模型、无LLM图模型、LLM增强图模型。

通过消融区分语义、历史结构与模型复杂度的作用。

**实验E3：标签稀缺是否改善**

在固定标签比例下比较监督学习与一致性半监督学习。

报告在不同标签预算下的效果变化。

**实验E4：完整候选组合**

仅在E1—E3存在积极证据且资源可承受时，实现语义融合 + 时序图 + 联合损失的组合模型。

对组合模型还需做去语义、去图、去一致性损失的独立消融。

### 4.2 评价指标

检测主指标保持业务一致：

- 每日固定Top 10下的TP@10；
- Precision@10、Recall@10；
- AP；
- AUROC、F1作为辅助指标；
- 分月份和分渠道稳定性；
- 训练耗时、推理耗时、模型参数量、资源使用和费用。

必须与已冻结的原残差模型及匹配输入的强树模型比较。

在相同日期和预算下核对实际入选交易名单。

建议按天进行有配对结构的重采样，报告新增捕获、损失、净变化及不确定性；同时报告多个固定随机种子的结果。

不得只挑选最好的模型seed或单个有利月份进行宣传。

2019已经被此前项目使用和观察。再次查看只能标为历史参考或复用评测，不能包装成新的独立留出测试。

如果需要宣称新模型对未来数据具有可靠提升，应另行取得合法来源、冻结新评测协议，并完成真正独立的测试。

### 4.3 对LLM价值的严格评价

只有B2/B3相对普通类别Embedding在同等输入和公平预算下表现出可复核增益，才可以将改进主要归因于预训练语义表示。

必须保留LLM无增益或效果下降的结果。

若增益仅来自新增类别信息、额外模型参数或更长训练时间，应如实报告。

## 5. 与调查Agent的并行开发边界

### 5.1 分支与文件所有权

当前共同基准提交：

`252fe35c8099910006122d2f603835396d8a380c`

建议：

- 检测研究分支：`codex/llm-semantic-detector`
- 调查Agent研究分支：`codex/dynamic-fraud-investigation`

两个分支从共同基准创建。

检测分支优先只新增：

`app/risk/semantic_detection/`

`app/cli/semantic_detection_*.py`

`config/semantic-detection/`

`tests/semantic_detection/`

`docs/semantic-detection/`

`requirements-semantic-detection.txt`

不要为了图模型临时修改整个 `app/risk/neural_v2.py` 的公共行为。

若需复用现有方法，优先增加适配器或独立导入，不破坏原有代码。

调查分支可以修改：

`app/investigation/`、`app/tools/`、`app/service/` 以及自己的测试和实验资料。

双方不得同时修改同一批共享文件。尤其是`README.md`、共同CLI入口、依赖清单和调查任务数据合同，应在集成阶段统一处理。

不得要求任何一方删除、覆盖、重命名另一方尚未合并的研究模块。

### 5.2 上下游接口合同

新检测模型的输出仍然是风险排序分数，不是欺诈认定。

必须提供与现有告警队列兼容的适配层：

- `transaction_id`
- `user_id`
- `event_time`
- `score`
- `day_rank`
- `tie_hash`
- 检测模型版本、来源指纹与特征版本等附加元数据

核心队列字段的实际定义应以现有冻结合同为准，附加元数据另行存储，不得随意扩展到破坏原消费者校验。

新旧检测模型必须具有独立、可追溯的artifact和release ID。

下游Agent只消费经过注册和验证的告警身份，不依赖具体神经网络结构。

**不得让下游Agent把LLM Embedding分数直接解释成欺诈概率或因果证据。**

### 5.3 模型发布规则

现有`neural_v2_ensemble`继续作为默认检测器。

新检测器先注册为`challenger`，运行影子评测，不自动替换生产式演示入口。

任何替换必须满足：

- 上游事实和标签隔离验证通过；
- 检测指标、成本和不确定性报告完整；
- 原模型成绩仍可复现；
- 新告警适配器通过来源、身份和排序验证；
- 下游Agent在新旧模型来源下均能正确识别绑定的版本；
- 用户明确批准升级。

## 6. 验收门槛

### Gate 0：可行性审计

交付：

- 可用于Embedding的类别字段清单；
- 来源、时间可用性和类别释义审计；
- 模型及数据规模预算；
- 无未来信息泄露的设计文档；
- 与现有Agent并行的文件所有权清单。

若类别语义信息不足，不得为了通过验收编造描述。可将研究退化为有意义的类别嵌入和时序建模对照，并如实说明原论文LLM部分不适用。

### Gate 1：LLM语义增强最小可运行模型

交付：

- 冻结的文本Embedding编码器和缓存；
- 普通类别Embedding对照；
- E1研究报告；
- 可复现的训练与预测入口；
- 全部数据隔离测试。

通过后再决定是否进行图学习。

### Gate 2：时序图与半监督研究

交付：

- 严格过去邻域构建器；
- 时间一致性、同时间戳、跨用户、未来节点等专项测试；
- 图模型、无LLM图模型、半监督损失的消融；
- GPU/CPU资源和运行成本报告。

若成本明显超过业务收益，允许停止完整TGAT复现。

### Gate 3：业务评价与模型集成

交付：

- 固定Top-K模型对照；
- 新旧交易名单差异；
- 误报、漏报、稳定性与时间成本；
- 模型及特征来源审计；
- 适配到现有调查Agent的独立演示；
- 是否建议替换原检测器的研究结论。

**Gate 3不要求新模型必然胜出；要求结论真实、可解释、可复核。**

## 7. 质量和安全测试

至少覆盖：

- 模型输入不得包含标签或未来结果。
- 任何验证/测试样本不得在训练中通过图结构或一致性损失泄露。
- 训练与推理的特征字段必须一致。
- MCC未知、缺失、格式不合法时安全回退。
- 卡编号按用户身份隔离。
- 图邻居不得包含未来或同刻禁止访问的交易。
- 同一模型、同一输入可稳定重放推理。
- 模型重新加载后的分数在明确数值容差内一致。
- 类别说明不得引用未经验证的真实商户信息。
- 新研究运行不得修改已冻结模型权重及研究包。
- 不同分支合并后，现有MCP、Harness、Memory和人工审阅测试必须保持通过。

## 8. 资源约束

首先完成零付费本地审计。

Embedding模型优先在本地运行，必要时租用有明确预算的GPU。

大模型不必对每笔交易重复编码相同类别文本。

不允许未经用户授权使用付费模型API、租赁GPU、上传源交易数据或下载使用条件不明的数据。

若资源不足，先完成轻量级语义对照，不应因为论文使用4090 24GB GPU就强制上马完整模型。

## 9. 必须保留的研究失败

开发过程必须保存：

- 训练失败和数据错误；
- 无LLM与有LLM的负结果；
- 时序图与简单模型的成本比较；
- 发现的数据泄露和修复；
- 验证指标与已观察测试指标的区别；
- 决定不采用某个模型的技术理由。

实验结论不得通过删除失败记录、反复读取测试集或修改既有结果进行美化。

## 10. 最终交付

开发Agent应完成：

1. 可独立运行的LLM语义增强检测研究模块。
2. E1—E4中已满足准入的实验与消融报告。
3. 新旧检测模型的固定容量对照。
4. 预处理、Embedding缓存、模型权重和输入来源的版本说明。
5. 完整的测试及复现步骤。
6. 与下游调查Agent兼容的可选告警接入适配器。
7. 一份面试技术说明，能够明确解释：
   - 为什么金融类别可以使用语义Embedding；
   - 语义Embedding与普通类别Embedding有何不同；
   - LLM是否真的提升了效果；
   - TGAT增加了什么历史信息；
   - 半监督为什么能够利用无标签数据；
   - 采用何种手段防止未来信息泄露；
   - 为什么新模型值得或不值得替换原模型。

## 11. 开发执行规则

从Gate 0开始，优先完成可验证的实现，不将整篇论文复现作为强制交付前提。

每阶段先提交可核查的数据、代码和实验回执，再做下一阶段。

如果简单模型效果更好，应保留简单模型，不得为了体现LLM使用而强行选取复杂方案。

双方开发不得更改彼此实验结果、模型输入、调查证据或历史研究包。

任何共享接口变更必须在独立集成PR中进行，并经过双方回归测试。
