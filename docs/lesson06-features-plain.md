# 第六批：把一笔交易变成模型能用的线索

这次先理解下面的例子即可。代码版本、文件哈希等是方便复查的记录，暂时不用背。

## 1. 我们现在做什么

上一批已经选好了研究数据。这一批要给每笔交易补上几列信息：过去消费了几次、花了多少、是否见过这个商户标识。

这些信息叫“特征”。直白地说，就是交给检测模型的线索。

整个项目目前的顺序：

**准备数据（已完成首版） → 计算线索（本批） → 训练和比较检测模型（接下来） → Agent 帮人查预警（后续）。**

## 2. 用五笔交易理解

下面都是自建教学数据，金额只是教学单位：

| 时间 | 同一用户的消费 | 商户 |
|---|---:|---|
| 09:00 | 20 | 甲 |
| 09:40 | 30 | 乙 |
| **10:00，正在判断** | **100** | **乙** |
| 10:00，另一笔 | 500 | 丙 |
| 10:10 | 900 | 乙 |

判断 10 点这笔 100 时，程序算出：

- 过去一小时 2 笔：09:00 和 09:40；正好在一小时前的记录也算。
- 过去一天金额合计 50：20 + 30。假设此前一天没有其他记录。
- 过去 30 天见过商户乙：是，因为 09:40 已经在乙消费过。

不能把当前的 100 加进过去。10:10 的 900 当时还没发生，更不能加。两笔都记为 10:00 时，不知道谁先发生，因此互相也不算过去。

程序替我们严格执行这些规则，不需要让大语言模型心算。

## 3. 算出这些，为什么有用

孤立地看“消费 100”，不知道是否值得怀疑。如果同时知道此人过去一小时交易很多、金额明显超过其以往水平，调查线索就更充分。

但线索不等于结论。正常客户也可能突然多次消费；已有商户也可能出现欺诈。下一阶段让检测模型利用训练样本学习这些线索与标签的关系，并用留出的数据检查效果。

## 4. 特征、标签、Agent，分别是什么

| 名称 | 直白解释 | 在项目里的作用 |
|---|---|---|
| 特征 | 判断时可以看到或计算的线索 | 金额、此前一小时次数等，交给检测模型 |
| 标签 | 训练和评测用的答案 | 本合成数据里的 Yes/No；不交给调查 Agent |
| 检测模型 | 从训练例子中学习的筛选器 | 给交易打分，筛选值得调查的预警 |
| Agent | 会根据查询结果继续查的助手 | 后续查询历史、引用证据、说明资料缺口 |

项目里的检测模型与大语言模型是两个不同组件。先用规则、逻辑回归、树模型做检测；大语言模型以后用于工具调查，不替代本批的精确计算。

这批还没有训练模型，也没有完成真实模型调查。

## 5. 必须记住的三个错误

**把未来混进过去。**例如拿 10:10 的消费帮助判断 10:00 的交易，考试成绩会虚高；真正运行时却拿不到这条信息。这种偷看后来信息的问题通常叫“数据泄漏”。

**把别人的历史算到这个人身上。**历史必须按用户分别统计。本版用户统计可以包含该用户不同卡的交易。

**把“不知道”填成 0。**如果没有可用的上一笔交易，间隔时间应表示未知，而不是 0 秒。0 秒和不知道不是一回事。过去 30 天无记录，也不能直接判断用户正常。

## 6. 本批程序实际会保存哪些线索

当前金额、小时、星期几、渠道、MCC（商户类别码）；此前一小时、一天、七天、三十天的交易次数；一天和三十天的金额净和；三十天内是否见过当前商户标识；是否有历史；距离快照内上一笔交易的时间。

“金额净和”会保留负数相抵的效果，不能未经核实把它称为支出总额。“见过商户标识”也不能直接叫去过同一家实体门店。

保存交易 ID、用户 ID 和训练/验证/测试标记，是为了对账和追溯，不自动把它们交给模型作为预测线索。

## 自己运行这个例子

在项目根目录 PowerShell 运行，几乎立即返回，不联网、不需要 API Key：

```powershell
.\.venv\Scripts\python.exe -X utf8 -B -m app.cli.feature_demo
```

你会直接看到中文说明和三个结果：**2 笔、50、见过商户乙**。

验证计算是否正确：

```powershell
.\.venv\Scripts\python.exe -B -m pytest -q -p no:cacheprovider tests/test_risk_features.py
```

暂时不必读全部代码。想定位核心时：`app/risk/features.py` 负责计算，`app/cli/feature_demo.py` 提供上面的例子。大型数据的执行结果会另记在本批结果页。
