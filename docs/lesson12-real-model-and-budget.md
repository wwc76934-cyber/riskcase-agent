# 第十二课：把演示策略换成真正的大模型接口

2026-10-18 更新：真实接口认证已成功，但完整报告仍未验收；本课起初的“没有运行”描述为上批状态。最新排查与一次格式纠正见 [第十三批](live-v2-format-repair.md)。

先看进度：数据分析、检测模型和离线调查已经有实际结果。这一批把硅基流动客户端写好，并通过模拟接口验证。**真实模型还没有运行：当前项目没有可用密钥。**

你这次先理解三个问题：模型到底收到什么、程序怎样接住它的回答、失败之后怎样处理。

## 1. 这次到底换了什么

想象一名分析师收到一笔 803.34 的交易预警。此前离线演示中，“接下来查一小时，再查三十天”是我们用 Python 写死的策略。这次给这个位置接入硅基流动提供的 `Pro/zai-org/GLM-5.1`，让模型根据回执决定下一步。

我们没有重新训练这个大模型。这里的“接入”就是：Python 通过 HTTP 发一份 JSON，平台运行模型，再返回一份 JSON。它与前面用 PyTorch 训练欺诈检测器是两件事。

| 部分 | 这次是否改变 | 负责什么 |
|---|---|---|
| 检测器 | 沿用冻结结果 | 给交易打分，决定哪些值得审核 |
| 客户端 | 新增硅基流动 HTTP 实现 | 把任务发给模型，接收模型回答 |
| 调查工具 | 沿用三个受限工具 | 读取当前交易，计算过去的次数、金额和商户记录 |
| Agent 控制循环 | 继续复用 | 执行模型提出的工具请求，把回执放入消息历史 |
| 结论检查 | 继续使用 | 拒绝无来源、数字不符、窗口不符的结论 |

所以，Agent 并不是一个特别的模型名称。我们搭建的是“模型选择下一步 + 工具执行 + 程序管理过程”的系统。

## 2. 一次交互，具体传什么

第一次请求包含任务说明、允许的工具名称、工具参数格式。工具接口已经绑定这一个用户和调查时间，模型不能另填别人的账号。

模型可能返回：

```json
{"name":"summarize_history","arguments":{"lookback_hours":1}}
```

这是请求，还不是查询结果。Python 检查参数，再查询本地 case 数据库。工具可能返回“此前一小时 0 笔，窗口覆盖完整”，并附证据编号。

下一次请求会带上前面的消息和这条工具回执。模型才有依据决定：频次线索不支持，是否继续查金额和商户。**消息历史的作用，就是让下一次模型知道刚才已经查过什么、查到了什么。**

模型不会直接打开整个原始数据库。外发的是任务说明、工具说明和工具实际返回的有限事实。当前源是合成数据；目标标签不在 case 库，也没有读取标签的工具。

## 3. API 成功，为什么还要检查结论

假设服务器返回 HTTP 200，可以理解为“信送到了，也拿到了回信”。它不能证明回信内容正确。

我们分三步检查：

1. 接口层：回答是不是合法 JSON，有没有被截断，消息格式能否解析。
2. 工具层：工具是否存在，参数是否在允许范围，调用预算是否用完。
3. 结论层：模型引用的证据是否真实存在，证据是否支持它选的结论。

例如，工具已经返回一小时 0 笔，模型却交“高频线索成立”，程序会拒绝生成有效报告。程序不会因为模型语气肯定就接受。

本版最终只接受三种预定义检查项和三个结论状态。通过检查后，程序把已核对数字填入中文报告。自由写作以后可以扩大，但要先补相应的校验和评测。

## 4. 为什么每查一次，费用还可能变化

平台按 token 计量。先把 token 理解为模型处理文字的计量单位，它不等于中文字数，也不等于字节数。

输入包含任务、工具说明、已有对话和回执。随着消息历史变长，后一次请求可能比前一次贵。输出是模型本次生成的内容；推理 token 若计入平台的 completion_tokens，就不能再重复加一次。

本批配置：最多 6 次请求、每次最终输出最多 1024 token、关闭思考模式；单次 HTTP 超时 45 秒，整轮设 180 秒截止检查。开始下一请求前也会检查剩余时间。它不是能够强制终止远程计算的硬截止服务。

每轮按 1 元本地估算阈值控制，整个项目账本按 20 元控制。请求前先留出一笔估算额度；收到有效 usage 后，按返回数量重新计算。输入预留使用“UTF-8 字节数 + 额外余量”的启发式方法，没有声称它是模型 tokenizer 的严格上界。

价格配置采用 2026-10-17 查到的 GLM-5.1 较高输入长度档：输入 8 元/百万 token，输出 28 元/百万 token，不扣缓存折扣。实际价格和账单仍以[硅基流动价格页](https://cloud-rd.siliconflow.cn/pricing)及账户明细为准。

**这是本地估算和停止规则，不是平台保证的费用硬上限。** 其他客户端的消费不在这份账本里，重建或删除账本也不会重置平台消费。平台若返回超出预留的 usage，我们先记录已知估算，再停止后续调用。

参数含义依据[官方接口文档](https://docs.siliconflow.cn/docs/api/chat-completions-post)。思考预算与最终输出预算不同；[官方思考模式说明](https://docs.siliconflow.cn/docs/userguide/capabilities/reasoning)也提示不同模型的预算约束能力存在差异。本模型对这些参数的实际兼容性仍待真实请求验证；如果不兼容，本批直接报错，不自动换模型或放开预算。

## 5. 超时为什么不能直接重试

你发出请求后，没有及时收到结果，可能有两种情况：平台根本没有开始；平台已经计算，但回信没送回来。第二种情况可能已经计费。

因此当前版本不自动重试；不知道 usage 时，费用账本继续保留原先预留的估算，并把这次标成“不确定”。401、429、服务错误、响应截断等也会停止本轮，不生成伪装成功的调查报告。

这和风控业务中的一个原则相通：**未知要单独记录，不能当作零、正常或成功。** 不过 API 失败与交易风险是两种不同状态，不能因 API 超时就认定交易高风险。

## 6. 你可以运行什么

在项目根目录 PowerShell，先检查准备情况。这条命令不联网、不计费：

```powershell
.\.venv\Scripts\python.exe -X utf8 -B -m app.cli.investigate_live --preflight
```

`case_ready: true` 表示本地案例可用。`credential_present: false` 只表示当前进程没有配置环境变量密钥，不会打印密钥。

模拟完整 HTTP 流程，不联网、不计费：

```powershell
.\.venv\Scripts\python.exe -X utf8 -B -m app.cli.investigate_live --mock
```

这里的平台回复来自写好的离线策略。即使报告全部通过，也只能证明接口、工具、证据校验能连起来，不能证明真实模型会调查。

真正调用模型时，在本地交互终端运行：

```powershell
.\.venv\Scripts\python.exe -X utf8 -B -m app.cli.investigate_live --live --prompt-key
```

终端会隐藏输入；输入密钥后按回车。密钥只留在本次进程内存，不写入文件、Git 或运行日志。不要贴到聊天。按 Ctrl+C 可以中断；已发送请求仍可能计费。

每次输出一个新的运行目录。先看 `summary.json` 的 `status` 和 `last_error_code`，再看 `usage.json` 的次数与费用估算。成功时还有 `report.md`；`trace.json` 保存交互和工具回执，不保存供应商的 reasoning_content 字段。

验证某一次成功运行，把下面路径换成命令输出的目录：

```powershell
.\.venv\Scripts\python.exe -X utf8 -B -m scripts.verify_case_run --summary runs/你的运行目录/summary.json
.\.venv\Scripts\python.exe -X utf8 -B -m scripts.verify_live_run --summary runs/你的运行目录/summary.json
```

第一条核对事实和引用，第二条复算保存的 usage 费用估算。二者都不能代替真实业务评测。下一批才会逐步建设更多调查任务，与相同数据权限的固定流程比较。
